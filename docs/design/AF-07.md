# Design AF-07 · Cadastro de profissionais

História: docs/stories/AF-07.md · Status do design: proposto

Este design segue a stack, a estrutura de pastas e os padrões transversais de docs/design/AF-01.md (seções 1 a 3) e as extensões de docs/design/AF-02.md, docs/design/AF-05.md e docs/design/AF-06.md. Aqui só aparece o que muda ou o que é novo. **Não há dependência nova.**

---

## 1. Resumo da solução

- Novo módulo `src/modules/professionals/` (routes/service/repository), com a entidade `professionals` ligada ao negócio do dono (`business_id`) e a tabela de associação N:N `professional_services`. O negócio vem sempre da sessão (`businessesRepository.findByOwnerId`). Nenhuma rota aceita `businessId` do cliente.
- API REST em `/api/professionals`: listar, ler, criar, editar (nome e serviços), remover (lógico), trocar e remover a foto. A foto é servida em `/media/professionals/:file`.
- **Remoção lógica** (decisão 3 do gerente): a coluna `removed_at` marca o profissional como removido. A linha fica no banco, então o histórico de agendamentos continua com o nome (critério 20). O removido some da listagem do dono e dos contratos públicos.
- **Bloqueio atômico da remoção** (decisão 1): `DELETE` roda numa transação que marca a remoção e conta os agendamentos futuros pela porta `appointments` com a mesma conexão `tx`. Se a contagem for maior que 0, a transação desfaz tudo e a API responde 409 com `futureAppointmentsCount`. A porta devolve 0 até o AF-11. Realocar e cancelar em lote ficam para AF-11/14/15. O AF-11 recebe um contrato de trava (`claimForBooking`) que impede um agendamento órfão.
- **Porta de agendamentos** (padrão do AF-06): `appointments-port.js` sai de `src/modules/services/` e vai para `src/modules/appointments/`, onde o AF-11 vai morar. A porta ganha `countFutureByProfessional(businessId, professionalId, nowIso, conn)`.
- **Serviços do profissional**: `serviceIds` na criação e na edição. A edição substitui a lista inteira na mesma transação. Só serviços do mesmo negócio entram, e um ID de outro negócio ou inexistente dá o mesmo erro de validação. A chave primária `(professional_id, service_id)` impede duplicatas, e FKs compostas com `business_id` impedem no banco um vínculo entre negócios diferentes.
- **Serviço desativado mantém o vínculo** (decisão 6), marcado como `active: false` na resposta. "Agendável" é calculado na consulta (`removed_at IS NULL` e ao menos um serviço com `active = 1`), então reativar o serviço restaura o efeito sem escrita nenhuma no profissional (critério 8). Profissional sem serviço ativo não é agendável (decisão 7, contrato para AF-09/10).
- **Nome duplicado é permitido, com aviso** (decisão 4): coluna `name_key` com índice **não único**. A resposta de criação e de edição traz `warnings` quando há outro profissional ativo com a mesma chave. A tela avisa antes de salvar, sem bloquear.
- **Regra de nome visível** (AF-06 item 1, critério 3): `validateText` em `src/shared/validation.js` passa a exigir conteúdo visível, recusar letras invisíveis e limitar marcas combinantes. A regra vale num lugar só, para o nome do profissional, do serviço e do negócio e para o endereço. A chave normalizada (`textKey`) também passa a morar em `validation.js`. `serviceNameKey` vira um alias dela.
- **Foto com o mesmo pipeline do logo** (decisão 5): `logo-image.js` vira um invólucro de `src/images/square-image.js` (PNG/JPG por assinatura, até 2 MB, 256x256, sem metadados). **Novo limitador de concorrência de imagem** (`src/images/image-limiter.js`, fecha AF-05 item 2), dividido entre logo e foto: 2 processamentos simultâneos, fila de 4, e acima disso 503 `IMAGE_BUSY`.
- **Cache de 1 dia** (decisão 8, AF-05 item 4): a foto sai com `Cache-Control: public, max-age=86400`, sem `immutable`. O logo passa a usar o mesmo valor, o que fecha o AF-05 item 4.
- Limite de **50 profissionais ativos por negócio** (decisão 8), checado na mesma transação do `INSERT`.
- Guards próprios por rota via `createRouteGuards` (buckets novos `professionalWrite` e `professionalPhoto`). Leituras só com `authOnly()`, como no AF-06. O limitador por usuário continua em memória (decisão 9).
- Nova tela `/profissionais` (`web/profissionais.html`), com link a partir de `/servicos`.

## 3. Modelo de dados

`src/db/migrations/005_professionals.sql` (nova; as migrações 001 a 004 não são editadas):

```sql
-- Necessário para a FK composta (service_id, business_id). Portável: o PostgreSQL aceita
-- FK para colunas cobertas por índice único não parcial.
CREATE UNIQUE INDEX services_id_business_id_unique ON services(id, business_id);

CREATE TABLE professionals (
  id           TEXT PRIMARY KEY,                    -- UUID v4
  business_id  TEXT NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  name         TEXT NOT NULL,                       -- trim + NFC, até 100 code points, como digitado
  name_key     TEXT NOT NULL,                       -- textKey(name); NÃO é único (homônimos, decisão 4)
  photo_key    TEXT,                                -- professionals/<uuid>.png; NULL = sem foto
  removed_at   TEXT,                                -- NULL = ativo; remoção lógica (decisão 3)
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  CONSTRAINT professionals_id_business_id_unique UNIQUE (id, business_id),
  CONSTRAINT professionals_removed_photo_check CHECK (removed_at IS NULL OR photo_key IS NULL)
);
CREATE INDEX professionals_business_id_removed_at_idx ON professionals(business_id, removed_at, name_key);
CREATE INDEX professionals_photo_key_idx ON professionals(photo_key);

CREATE TABLE professional_services (
  professional_id  TEXT NOT NULL,
  service_id       TEXT NOT NULL,
  business_id      TEXT NOT NULL,
  created_at       TEXT NOT NULL,
  PRIMARY KEY (professional_id, service_id),
  FOREIGN KEY (professional_id, business_id) REFERENCES professionals(id, business_id) ON DELETE CASCADE,
  FOREIGN KEY (service_id, business_id) REFERENCES services(id, business_id) ON DELETE CASCADE
);
CREATE INDEX professional_services_business_id_service_id_idx ON professional_services(business_id, service_id);
```

- **Sem duplicatas** (critério 9): a chave primária `(professional_id, service_id)` impede duplicatas. O serviço também tira repetições da lista antes de gravar e usa `INSERT ... ON CONFLICT (professional_id, service_id) DO NOTHING`, que é portável (SQLite 3.24 ou superior e PostgreSQL). Uma lista com o mesmo ID duas vezes nunca chega à constraint nem gera 500.
- **Mesmo negócio no banco**: as duas FKs compostas fazem o banco recusar um vínculo entre profissional e serviço de negócios diferentes, mesmo com bug na aplicação. A validação de `serviceIds` (seção 5.2) roda antes, então uma violação de FK é bug e vira 500 pelo caminho normal. O teste de repositório prova a regra com `INSERT` direto.
- `ON DELETE CASCADE` acompanha a cadeia existente (usuário → negócio → serviços). Não há exclusão física de profissional nem de serviço pela aplicação. Quando o AF-11 criar `appointments`, a FK para `professionals` deve ser `ON DELETE RESTRICT` (R7).
- O `CHECK` `professionals_removed_photo_check` garante que um removido não guarda foto (6.5). É SQL portável.
- `name_key` serve só para o aviso de homônimo e para a ordenação estável (`ORDER BY name_key, id`, critério 21).
- O índice `(business_id, removed_at, name_key)` cobre a listagem do dono e a contagem do limite. O índice `(business_id, service_id)` cobre a consulta inversa (critério 10). `photo_key` tem índice para a rota `/media`, como `businesses_logo_key_idx`.

Em `src/http/errors.js`, novo erro:

```js
export class ImageBusyError extends AppError {
  constructor(retryAfterSeconds = 5) {
    super(503, 'IMAGE_BUSY', 'Muitas imagens sendo processadas agora. Tente novamente em instantes.');
    this.retryAfterHeader = retryAfterSeconds;   // Retry-After, mesmo mecanismo do RateLimitedError
  }
}
```

- O 503, e não o 429, deixa claro que o motivo é a carga do servidor e não o uso da pessoa. O critério 14 aceita fila ou 429/503.
- Pico estimado: cerca de 64 MiB por imagem de 4096x4096 decodificada, mais a saída. Com 2 simultâneas, o pico fica perto de 150 MiB. Hoje não há teto (o AF-05 mediu cerca de 200 MB com 8 uploads). Cada requisição na fila segura o corpo, de até 2 MiB, ou seja, no máximo 8 MiB.
- `businessesService` e `professionalsService` recebem `imageLimiter` e chamam `imageLimiter.run(() => process(buffer))`. O limite vale só para o processamento: `storage.put` e a transação ficam fora da vaga.
- A ordem continua a do AF-05: `requireAuth`, limite por usuário, limite por IP, leitura do corpo (limitada a 2 MiB), handler, busca do negócio e do profissional (404 antes de processar), e por fim o limitador.

## 5. Interfaces

### 5.1 API

Todas as rotas `/api/professionals*` exigem sessão (`requireAuth`). Sem sessão, a resposta é 401 `UNAUTHENTICATED` e nada é lido nem gravado. As mutações passam pelo hook de CSRF existente (403 `FORBIDDEN_ORIGIN`, critério 25). Dono sem negócio recebe **409 `BUSINESS_REQUIRED`** ("Cadastre seu negócio antes de cadastrar profissionais.") em todas as rotas, o mesmo código do AF-06 (critério 2), e o front redireciona para `/onboarding`.

Representação (só via `toOwnerProfessional`, o único caminho de serialização):

```json
{ "id": "…", "name": "Ana Souza", "photoUrl": "/media/professionals/<uuid>.png",
  "services": [ { "id": "…", "name": "Corte", "active": true },
                { "id": "…", "name": "Coloração", "active": false } ],
  "bookable": true, "createdAt": "…", "updatedAt": "…" }
```

- `businessId`, `nameKey`, `photoKey` e `removedAt` não são expostos. `photoUrl` é `null` sem foto, e o front mostra o avatar padrão.
- `services` vem na ordem do AF-06 (`active DESC, name_key, id`). Serviço desativado aparece com `active: false` (critério 8).
- `bookable` vale `true` se e somente se existe ao menos um serviço com `active: true`. É o mesmo critério dos contratos de 5.5 (critério 7), e a tela usa o campo para o selo "Não aparece para clientes".

O `:id` precisa casar `PROFESSIONAL_ID_RE`, o mesmo UUID v4 de `SERVICE_ID_RE`. Senão a resposta é 404 `PROFESSIONAL_NOT_FOUND`. Profissional de outro negócio, inexistente e removido dão a mesma resposta: 404 `PROFESSIONAL_NOT_FOUND`, "Profissional não encontrado." (critério 24). Nenhuma mensagem repete valores enviados (critério 5).

**`GET /api/professionals`** (`authOnly()`): 200 `{ "professionals": [ … ] }`, só não removidos, ordenados por `name_key ASC, id ASC` (critério 21). Não há filtro.

**`GET /api/professionals/:id`** (`authOnly()`): 200 `{ "professional": {…} }` ou 404.

**`POST /api/professionals`** (guards próprios, bucket `professionalWrite`)

Request (`application/json`, até 16 KB): `{ "name": "Ana Souza", "serviceIds": ["…", "…"] }`. `serviceIds` é opcional: ausente equivale a `[]` (rascunho, critério 7). Qualquer outro campo (`businessId`, `id`, `photoKey`, `removedAt`...) é ignorado. A foto é enviada depois, em `PUT /:id/photo` (decisão 14).

| Status | Quando | Corpo |
|---|---|---|
| 201 | criado | `{ "professional": {…} }`, mais `"warnings": [{ "code": "PROFESSIONAL_NAME_DUPLICATE", "field": "name", "message": "Já existe um profissional com este nome. Confira se não é a mesma pessoa." }]` quando houver homônimo ativo |
| 400 | validação (todos os campos de uma vez) | `VALIDATION_ERROR` com `fields` (`name`, `serviceIds`) |
| 409 | 50 profissionais ativos | `PROFESSIONAL_LIMIT_REACHED`, "Você atingiu o limite de 50 profissionais. Remova um profissional para cadastrar outro." |
| 409 | sem negócio | `BUSINESS_REQUIRED` |
| 429 | rate limit (usuário ou IP) | `RATE_LIMITED` |

**`PATCH /api/professionals/:id`** (guards próprios, bucket `professionalWrite`)

Request: subconjunto de `{ name, serviceIds }`. Só os campos presentes (a chave existe) são validados e gravados. Se `serviceIds` vier, **substitui** a lista inteira (`[]` limpa tudo). Corpo sem nenhum dos dois campos dá 400 "Nada para atualizar.". Respostas: 200 `{ "professional": {…}, "warnings"?: [...] }`, 400, 404 e 429. O aviso de homônimo só aparece quando `name` vem no corpo e outro profissional ativo, que não seja o próprio, tem a mesma chave.

**`DELETE /api/professionals/:id`** (guards próprios, bucket `professionalWrite`; sem corpo)

| Status | Quando | Corpo |
|---|---|---|
| 204 | removido (lógico); a foto é apagada | – |
| 404 | inexistente, de outro negócio ou **já removido** | `PROFESSIONAL_NOT_FOUND` |
| 409 | há agendamentos futuros (critério 17) | `{ "error": { "code": "PROFESSIONAL_HAS_FUTURE_APPOINTMENTS", "message": "Este profissional tem agendamentos futuros. Realoque ou cancele esses agendamentos antes de remover.", "futureAppointmentsCount": 3 } }` |
| 429 | rate limit | `RATE_LIMITED` |

O 409 não altera nada: nome, serviços e foto continuam iguais. A segunda remoção dá 404, porque o profissional deixou de existir para o dono. A tela trata o 404 do `DELETE` como "já removido" e recarrega a lista.

**`PUT /api/professionals/:id/photo`** (sub-plugin binário, guards próprios, bucket `professionalPhoto`)

Mesmo contrato do `PUT /api/business/logo` (design AF-05, 5.1). O corpo é binário (`application/octet-stream`, `image/png` ou `image/jpeg`; o valor é ignorado na detecção) e vai até 2.097.152 bytes.

| Status | Quando | Corpo |
|---|---|---|
| 200 | salva | `{ "professional": {…} }` com o novo `photoUrl` |
| 401 / 404 / 409 `BUSINESS_REQUIRED` | sessão, profissional ou negócio | – |
| 413 | acima de 2 MiB | `PHOTO_TOO_LARGE`, "A foto deve ter no máximo 2 MB." |
| 415 | outro `Content-Type` | `UNSUPPORTED_MEDIA_TYPE` |
| 422 | não é PNG/JPEG pela assinatura, vazio, corrompido ou acima de 4096x4096 | `INVALID_IMAGE` (mesmas mensagens do logo) |
| 429 | rate limit | `RATE_LIMITED` |
| 503 | limitador de imagem cheio (seção 4.2) | `IMAGE_BUSY` + `Retry-After: 5` |

**`DELETE /api/professionals/:id/photo`** (guards próprios, bucket `professionalPhoto`): 204, idempotente (sem foto também dá 204), e 404 como acima.

**`GET /media/professionals/:file`** (público, usado pelo AF-09)

- `:file` precisa casar `PHOTO_FILE_RE = /^<uuid v4>\.png$/` (o mesmo de `LOGO_FILE_RE`). Senão a resposta é 404.
- O arquivo só é entregue se `professionals/<file>` estiver em `professionals.photo_key`, via `existsPhotoKey`. Arquivo substituído, removido ou de profissional removido dá 404 (critério 13).
- Headers: `Content-Type: image/png`, `Content-Disposition: inline; filename="foto.png"`, **`Cache-Control: public, max-age=86400`** (critério 15) e `Content-Security-Policy: default-src 'none'; sandbox`. O `nosniff` vem do helmet.
- **`GET /media/logos/:file` passa para o mesmo `Cache-Control: public, max-age=86400`** (fecha AF-05 item 4).

**Página**: `GET /profissionais` serve `web/profissionais.html`. Entra em `PAGES`, e `profissionais` já está em `RESERVED_SLUGS`.

### 5.2 Validação compartilhada

**`src/shared/validation.js` (alteração, regra única do AF-06 item 1)**

```js
// Letras e brancos invisíveis que não são \p{Cf}: U+115F, U+1160, U+3164 (Hangul filler),
// U+FFA0 (halfwidth Hangul filler), U+2800 (Braille em branco).
const INVISIBLE_CHARS = /[ᅟᅠㅤﾠ⠀]/u;
export const MAX_MARKS_PER_LETTER = 3;

/** Chave normalizada: NFC -> NFD -> remove \p{M} -> minúsculas -> colapsa \s+. Movida de serviceNameKey. */
export function textKey(text)                 // -> string
/** true se tem ao menos um \p{L}/\p{N}, nenhum caractere de INVISIBLE_CHARS,
 *  não começa com \p{M} e não tem mais de 3 \p{M} seguidos (na forma NFD). */
export function hasVisibleContent(text)       // -> boolean
```

`validateText(raw, max, messages)` ganha, depois do `hasForbiddenChars`: `!hasVisibleContent(text) || textKey(text) === ''`, que devolve `messages.invalid`. A checagem passa a valer para o nome do negócio e para o endereço, pelo `validateText` atual. `validateServiceName` passa a chamar `validateText` em vez de repetir as etapas. `serviceNameKey` vira `export const serviceNameKey = textKey`, então a chave não muda para os dados existentes (R5).

Exemplos rejeitados com "O nome contém caracteres inválidos.": `"́́"`, `"á̂̃̄"`, `"ㅤ"`, `"Anaㅤ"`, `"⠀"`, `"..."`, `"-"`. Exemplos aceitos: `"Ana"`, `"João"` (NFC ou NFD), `"Nguyễn"` (2 marcas), `"Dra. Ana"`, `"Ana 2"`, `"李"`.

### 5.5 Contrato para outras histórias

- **AF-09 / AF-10 (critério 7, decisão 7)**: um profissional é "ativo" quando `removed_at IS NULL` e "agendável" quando, além disso, tem ao menos um serviço com `active = 1`. Rotas públicas e cálculo de disponibilidade usam só `findBookableByBusinessId`, `findBookable` e `findBookableForService`, que é a consulta "qualquer profissional" do AF-10 (critério 10). Nunca `listByBusinessId`. Um serviço desativado nunca conta, mesmo vinculado (critério 8).
- **AF-11 (critério 19)**: a criação de agendamento, **dentro da sua transação**, chama primeiro `claimForBooking(professionalId, businessId, tx)` e aborta se `changes === 0`. A remoção grava `removed_at` com `UPDATE` antes de contar. As duas operações disputam a mesma linha: no SQLite, `BEGIN IMMEDIATE` e a fila do adapter serializam. No PostgreSQL, o `UPDATE` trava a linha, então uma operação espera a outra e a segunda vê o resultado da primeira. Nenhuma ordem produz agendamento futuro de profissional removido. O AF-11 também implementa `countFutureByProfessional` usando só `conn`, cria `appointments.professional_id` com `ON DELETE RESTRICT` e lê o nome de removidos com `findByIdIncludingRemoved` (critério 20). Se preferir snapshot, grava `professional_name` junto.
- **AF-11 / AF-14 / AF-15 (decisões 1 e 2)**: realocar e cancelar em lote, e a regra de "para quem realocar", entram com esses itens. A partir daí, o critério 18 ganha teste de ponta a ponta. O AF-14 acrescenta o link "Ver agendamentos" na mensagem de bloqueio.
- **AF-08**: horários são por `professionals.id`. Profissional removido não tem horários consultáveis, porque o filtro é `removed_at IS NULL`.

## 6. Fluxos

### 6.1 Criação (`create`)

1. `business = businessesRepository.findByOwnerId(ownerId)`. Se não houver, `ConflictError('BUSINESS_REQUIRED')`.
2. `validateProfessionalInput(input)`. Com erros, `ValidationError(fields)`.
3. `db.transaction(async (tx) => { ... })`:
   1. `countActiveByBusinessId >= 50` lança `ConflictError('PROFESSIONAL_LIMIT_REACHED')`.
   2. `findServiceIdsOfBusiness(business.id, serviceIds, tx)`. Se faltar algum ID, `ValidationError({ serviceIds: serviceIdsInvalid })`, a mesma resposta para inexistente e de outro negócio (critério 6).
   3. `insert` e `replaceServices`.
   4. `countSameName(business.id, nameKey, id, tx) > 0` gera o aviso `nameDuplicate`.
4. `findById` e 201 com `toOwnerProfessional` e `warnings`.

Duas criações simultâneas com 49 ativos geram exatamente uma linha e um 409, pela mesma técnica do AF-06.

### 6.2 Edição (`update`)

1. Negócio (409) e `PROFESSIONAL_ID_RE` (404).
2. `hasProfessionalFields` (400 "Nada para atualizar.") e `validateProfessionalInput(input, { partial: true })`.
3. Numa transação: `updateName`, ou `touch` se só vierem serviços. Se `changes = 0`, `NotFoundError`, o que cobre o profissional removido. Se `serviceIds` vier, `findServiceIdsOfBusiness` (400) e `replaceServices`. Aviso de homônimo como em 6.1.
4. `findById` e 200.

Concorrência (critério 27): cada PATCH é uma transação só. Dois PATCH simultâneos são serializados, e o último vence por inteiro: o nome e a lista de serviços de cada PATCH nunca se misturam com os do outro. Não há controle de versão, como no AF-06 (decisão 9 daquele design).

### 6.3 Remoção (`remove`, critérios 17, 19 e 20)

1. Negócio e id.
2. `nowIso = now().toISOString()` e então `db.transaction(async (tx) => { ... })`:
   1. `{ previousPhotoKey, changes } = markRemoved(id, business.id, nowIso, tx)`. Se `changes = 0`, `NotFoundError`.
   2. `count = await appointments.countFutureByProfessional(business.id, id, nowIso, tx)`.
   3. Se `count > 0`, lança `ProfessionalHasAppointmentsError(count)`. O `ROLLBACK` desfaz o passo 1, e nome, serviços e foto ficam intactos.
3. Depois do `COMMIT`, a foto anterior é apagada em melhor esforço (`cleanup`, como no logo). Ela já não é servida, porque `photo_key` é `NULL`.
4. Os vínculos em `professional_services` **ficam**. Eles não aparecem em lugar nenhum, porque todas as consultas filtram `removed_at IS NULL`, e preservam o contexto histórico.
5. Se a porta lançar um erro dentro da transação, há `ROLLBACK` e o erro sobe como 500. Aqui é o contrário do AF-06, que nesse caso desativa mesmo assim: na dúvida, não se remove (R6).

### 6.4 Foto (`setPhoto` / `removePhoto`)

`setPhoto` segue o `setLogo`:

1. Negócio e `findById` (404 antes de processar).
2. `png = await imageLimiter.run(() => processImage(buffer))`.
3. `key = professionals/<randomUUID()>.png` e `storage.put`.
4. Transação `setPhotoKey`. Se `changes = 0`, porque o profissional foi removido no meio, a chave nova é apagada e a resposta é 404. Erro, idem.
5. `cleanup(previousKey)`.

`removePhoto`: `setPhotoKey(null)` e depois `cleanup`. Cada upload gera uma chave nova, então a URL antiga dá 404 assim que a troca é gravada. O cache do navegador ou de uma CDN pode manter a imagem antiga por até 1 dia (R4).

### 6.5 Ordem dos hooks

A mesma do AF-06, seção 6.4: CSRF, `requireAuth`, limite por usuário da própria rota, limite por IP da própria rota, parser (JSON de 16 KB ou binário de 2 MiB no sub-plugin) e handler. Requisição sem sessão não consome limite nem lê o corpo.

## 8. Riscos

| # | Risco | Mitigação |
|---|---|---|
| R1 | Até o AF-11, o bloqueio da remoção nunca dispara (a porta devolve 0) e o critério 18 não tem teste de ponta a ponta | Decisão 1 do gerente. O contrato está testado com porta falsa e com a simulação de concorrência. O AF-11 tem como entrega obrigatória implementar `countFutureByProfessional` e `claimForBooking` (5.5). |
| R2 | A porta chamada dentro da transação, se usar o `db` global em vez de `conn`, trava a fila do adapter SQLite (deadlock) | O JSDoc da porta proíbe. O teste de serviço confere que a porta recebe `tx !== db`. O AF-11 testa a implementação real dentro de `remove`. |
| R3 | `MAX_DIMENSION` continua 4096 (o AF-05 sugeriu 2048) | Fotos de celular de 12 MP (4032x3024) seriam recusadas com 2048. O limitador limita o pico a cerca de 150 MiB. Se a memória do servidor for menor que 512 MiB, reduzir `imageProcessing.concurrency` para 1. |
| R4 | Com cache de 1 dia, uma foto removida ou trocada pode continuar visível no cache de navegador ou CDN por até 24 h | Cada upload gera uma URL nova, então a URL atual nunca mostra a foto velha. O servidor dá 404 na hora. Se o PO exigir efeito imediato, usar `no-cache` com ETag. |

## 9. Decisões registradas (ADR curto)

1. **Só o bloqueio atômico da remoção entra agora** (decisão 1 do gerente): 409 com `futureAppointmentsCount` pela porta `countFutureByProfessional`, que devolve 0 até o AF-11. Realocar e cancelar em lote ficam para AF-11/14/15.
2. **A regra de realocação fica para quando a realocação existir** (decisão 2).
3. **Remoção lógica** (decisão 3) com `removed_at`. A remoção é definitiva para o dono (sem reativar nesta história). O nome fica para o histórico, e a foto é apagada.
4. **Nome duplicado é permitido, com aviso** (decisão 4): `name_key` sem `UNIQUE`, `warnings` na resposta e aviso na tela antes de salvar.
5. **A foto usa o pipeline do logo** (decisão 5): PNG/JPG por assinatura, 2 MB, 256x256, sem metadados, com o código movido para `src/images/square-image.js`.
6. **Serviço desativado mantém o vínculo** (decisão 6) e é marcado `active: false`. "Agendável" é calculado na consulta, então reativar restaura o efeito sem escrita.
7. **Sem serviço ativo, o profissional não é agendável** (decisão 7). O contrato está em 5.5.
8. **Limite de 50 profissionais ativos e cache de 1 dia** (decisão 8). O logo passa ao mesmo cache (fecha AF-05 item 4).
9. **O limitador por usuário continua em memória** (decisão 9).
10. **Atomicidade portável sem `FOR UPDATE`**: a remoção faz `UPDATE` antes de contar, e o AF-11 faz `claimForBooking` (`UPDATE` sem efeito) antes de inserir. A disputa é sempre pela mesma linha.
11. **Mesmo negócio garantido no banco** por FKs compostas com `business_id`, além da validação. Inexistente e de outro negócio dão o mesmo 400 em `serviceIds` e o mesmo 404 no `:id`.
12. **`serviceIds` substitui a lista inteira** no PATCH, na mesma transação do nome. A lista aceita serviços ativos e desativados do negócio, para que reenviar a lista atual nunca falhe.
13. **Limitador de imagem compartilhado** entre logo e foto: 2 simultâneos, fila de 4, timeout de 10 s e 503 `IMAGE_BUSY` acima disso (fecha AF-05 item 2). `MAX_DIMENSION` fica em 4096 (R3).
14. **A criação é só JSON; a foto vai em `PUT /:id/photo`.** Mantém um único parser binário isolado (padrão do logo) e evita `multipart`.
15. **A regra de nome visível fica num lugar só** (`validateText`/`hasVisibleContent`/`textKey` em `validation.js`) e vale para negócio, endereço, serviço e profissional (AF-06 item 1).
16. **A porta de agendamentos mora em `src/modules/appointments/`**, onde o AF-11 vai implementá-la.
17. **Remover um removido dá 404**, porque o recurso deixou de existir para o dono. A tela trata como sucesso.
18. **Leituras sem rate limit**, como no AF-06 (item 2 daquela revisão).
