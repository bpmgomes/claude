# Design AF-01 · Cadastro de dono do negócio

História: docs/stories/AF-01.md · Status do design: proposto

Como esta é a primeira história, este documento também define a stack, a estrutura de pastas e as convenções que as próximas histórias devem seguir. As seções 1 a 3 valem para o projeto todo. Da seção 4 em diante, o conteúdo é só da AF-01.

---

## 1. Stack (decisão de projeto)

| Camada | Escolha | Motivo |
|---|---|---|
| Runtime | Node.js 22 (>= 22.13), JavaScript ESM (`"type": "module"`) | Já está instalado. Não precisa de etapa de build e a mesma linguagem roda no front e no back, então as regras de validação são compartilhadas. |
| HTTP/API | Fastify 5 | Tem `app.inject()` para testar a API sem abrir porta, logger (pino) com redação de campos, `bodyLimit` e plugins oficiais. |
| Banco | SQLite via módulo nativo `node:sqlite` (`DatabaseSync`) | Roda embutido, sem servidor e sem Docker. Não tem dependência nativa para compilar. Nos testes, cada caso usa um banco `:memory:` próprio. |
| Abstração de banco | Adapter próprio (`src/db/`) + repositórios | Permite trocar para PostgreSQL depois sem mexer em serviços e rotas. Ver 3.3. |
| Hash de senha | `bcryptjs` (bcrypt em JS puro) | Atende o critério "bcrypt/argon2" sem binário nativo. O custo é configurável: 12 em produção, 4 nos testes. |
| Sessão | Cookie HttpOnly com token opaco e tabela `sessions` no servidor | Já prepara o AF-02, que pede logout que invalida a sessão no servidor e expiração por inatividade. JWT foi descartado por isso. |
| Segurança HTTP | `@fastify/helmet` (CSP `default-src 'self'`), `@fastify/rate-limit` | A CSP sem `unsafe-inline` reduz o impacto de XSS. O rate limit mitiga a enumeração de e-mail (ver 7). |
| Frontend | HTML + CSS + JS ESM puros em `web/`, servidos pelo próprio Fastify (`@fastify/static`) | É o mais simples possível: sem bundler e sem framework. CSS mobile-first, pensado a partir de 360 px (AF-09). |
| Testes | `node:test` + `node:assert` (nativos) | Não exigem dependência extra. Um único comando roda tudo. |

Dependências de runtime (`dependencies`): `fastify`, `@fastify/cookie`, `@fastify/static`, `@fastify/helmet`, `@fastify/rate-limit`, `bcryptjs`. Nenhuma `devDependency` é necessária nesta história. Lint e CI ficam no AF-20.

O plano B, caso o `node:sqlite` traga algum problema, está no risco R1.

## 2. Estrutura de pastas (vale para todas as histórias)

```
package.json
.gitignore                    # node_modules/, data/, *.db
src/
  server.js                   # entrada: lê config, buildApp(), listen()
  app.js                      # buildApp(options) -> instância Fastify (plugins, rotas, estáticos)
  config.js                   # loadConfig(env) -> objeto de config congelado
  http/
    errors.js                 # AppError, ValidationError, ConflictError, UnauthorizedError + errorHandler
  db/
    index.js                  # createDatabase(config) -> Database (adapter)
    sqlite.js                 # SqliteDatabase implementa a interface Database
    errors.js                 # UniqueViolationError (independente de banco)
    migrate.js                # runMigrations(db) + CLI
    migrations/
      001_users_sessions.sql
  shared/                     # código puro, sem dependências, usado no back E no browser
    validation.js
  modules/
    accounts/                 # AF-01 (e depois dados de conta)
      accounts.routes.js
      accounts.service.js
      users.repository.js
    auth/                     # sessão e senha (AF-01 cria, AF-02/03 estendem)
      password.js
      sessions.repository.js
      sessions.service.js
      auth.plugin.js          # decora request.user; preHandler requireAuth
web/
  cadastro.html
  onboarding.html             # placeholder até AF-05
  css/app.css
  js/api.js                   # wrapper de fetch JSON + parse do formato de erro
  js/signup-controller.js     # lógica testável (sem DOM)
  js/signup-page.js           # liga o DOM ao controller
  js/onboarding-page.js
test/
  helpers/test-app.js         # buildTestApp(): banco :memory:, bcrypt cost 4, captura de logs
  unit/
  integration/
  web/
data/                         # banco local de desenvolvimento (gitignored)
```

Convenções:
- Cada funcionalidade de negócio fica em `src/modules/<dominio>/`, com três arquivos: `*.routes.js` (HTTP: parse, status e cookies), `*.service.js` (regras, sem nada de HTTP) e `*.repository.js` (SQL, só através do adapter). As rotas não acessam o banco diretamente.
- As dependências são injetadas por `buildApp`, que cria `db`, os repositórios e os serviços e os registra com `app.decorate('services', {...})`. Não há singletons globais, e por isso cada teste monta o seu app isolado.
- Nomes de arquivo em kebab/dot-case minúsculo. Colunas SQL em `snake_case`, JS em `camelCase`. O mapeamento é feito no repositório.
- IDs são UUID v4 (`crypto.randomUUID()`), nunca sequenciais expostos (ver AF-12).
- Datas são gravadas como texto ISO-8601 em UTC (`new Date().toISOString()`). A conversão para o fuso do negócio só acontece na apresentação (AF-10/AF-23).
- Mensagens para o usuário são em português. Códigos de erro em inglês, no formato `UPPER_SNAKE`.
- Testes ficam em `test/{unit,integration,web}/<nome>.test.js`.

## 3. Padrões transversais

### 3.1 Formato de erro da API

Todo erro tem a forma abaixo:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Verifique os campos destacados.", "fields": { "password": "A senha deve ter no mínimo 8 caracteres." } } }
```

- `fields` é opcional e é um mapa `campo -> mensagem`, com uma mensagem por campo.
- Status usados: 400 `VALIDATION_ERROR`, 401 `UNAUTHENTICATED`, 409 `EMAIL_TAKEN` (e outros conflitos), 413/415 vindos do Fastify, 429 `RATE_LIMITED` e 500 `INTERNAL_ERROR`.
- Em erro 500, a mensagem é sempre genérica ("Erro inesperado. Tente novamente."). Stack e detalhes vão só para o log, e o log é redigido (3.4).
- `src/http/errors.js` exporta as classes e `errorHandler(error, request, reply)`, registrado com `app.setErrorHandler`. Os erros de validação de schema e de content-type do próprio Fastify também são convertidos para este formato.

### 3.2 Configuração (`src/config.js`)

`loadConfig(env = process.env)` retorna:

| Chave | Env | Padrão | Testes |
|---|---|---|---|
| `port` | `PORT` | 3000 | – |
| `databasePath` | `DATABASE_PATH` | `./data/agendafacil.db` | `:memory:` |
| `bcryptCost` | `BCRYPT_COST` | 12 | 4 |
| `sessionTtlDays` | `SESSION_TTL_DAYS` | 7 | 7 |
| `cookieSecure` | `COOKIE_SECURE` | `true` se `NODE_ENV=production` | `false` |
| `rateLimit.enabled` | `RATE_LIMIT_ENABLED` | `true` | `false` (exceto no teste específico) |
| `rateLimit.signupMax` | – | 10 por minuto por IP | – |
| `logLevel` | `LOG_LEVEL` | `info` | `silent`, ou stream capturado |

`buildApp(overrides)` combina `loadConfig()` com `overrides`. Os testes sempre passam pelos overrides e nunca dependem do `process.env`.

### 3.3 Camada de banco (troca futura de SGBD)

Interface `Database` (JSDoc em `src/db/index.js`). Ela é **assíncrona** mesmo com o SQLite sendo síncrono, para que uma implementação em PostgreSQL entre no lugar sem mudar quem chama:

```js
/**
 * @typedef {Object} Database
 * @property {(sql: string, params?: unknown[]) => Promise<{ changes: number }>} run
 * @property {(sql: string, params?: unknown[]) => Promise<object|undefined>} get
 * @property {(sql: string, params?: unknown[]) => Promise<object[]>} all
 * @property {<T>(fn: (tx: Database) => Promise<T>) => Promise<T>} transaction
 * @property {(sql: string) => Promise<void>} exec   // usado só pelas migrações
 * @property {() => Promise<void>} close
 */
export function createDatabase({ databasePath }) // -> Database (SqliteDatabase)
```

Regras:
- Os placeholders são sempre posicionais (`?`). Um adapter de PostgreSQL futuro converte para `$1..$n`.
- O SQL dos repositórios fica restrito ao subconjunto portável: sem `AUTOINCREMENT`, sem funções exclusivas de SQLite, e o UUID é gerado na aplicação.
- O adapter traduz erros de driver para erros neutros. No SQLite, `SQLITE_CONSTRAINT_UNIQUE` (ou `errcode` 2067, ou mensagem com `UNIQUE constraint failed`) vira `UniqueViolationError { constraint }`. Os serviços só conhecem `UniqueViolationError`.
- Ao abrir a conexão: `PRAGMA foreign_keys = ON;` `PRAGMA journal_mode = WAL;` (o WAL só vale para arquivo, não para `:memory:`) e `PRAGMA busy_timeout = 5000;`.
- `transaction(fn)` usa `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`. Isso já atende o AF-11/AF-22, que vão precisar de serialização de escrita.

Migrações: arquivos `src/db/migrations/NNN_descricao.sql`, aplicados em ordem e registrados na tabela `schema_migrations(version TEXT PRIMARY KEY, applied_at TEXT NOT NULL)`. `buildApp` chama `runMigrations(db)` na inicialização, inclusive nos testes, onde o banco em memória começa vazio. Nunca edite uma migração já existente. Cada mudança de schema ganha um arquivo novo.

### 3.4 Logs sem dados sensíveis

O logger do Fastify é configurado com `redact: { paths: ['req.headers.cookie', 'res.headers["set-cookie"]', '*.password', '*.passwordHash', '*.password_hash', 'body.password'], censor: '[REDACTED]' }`. Os corpos de requisição não são logados. Os serviços nunca logam o objeto de usuário vindo do banco, só o `userId`.

## 4. Modelo de dados (AF-01)

`src/db/migrations/001_users_sessions.sql`:

```sql
CREATE TABLE users (
  id            TEXT PRIMARY KEY,           -- UUID v4
  name          TEXT NOT NULL,
  email         TEXT NOT NULL,              -- já normalizado: trim + lowercase
  password_hash TEXT NOT NULL,              -- bcrypt ($2a$/$2b$...)
  created_at    TEXT NOT NULL,              -- ISO-8601 UTC
  updated_at    TEXT NOT NULL,
  CONSTRAINT users_email_unique UNIQUE (email)
);

CREATE TABLE sessions (
  id            TEXT PRIMARY KEY,           -- UUID v4 (uso interno)
  user_id       TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash    TEXT NOT NULL,              -- SHA-256 hex do token do cookie
  created_at    TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  expires_at    TEXT NOT NULL,              -- last_seen_at + sessionTtlDays
  revoked_at    TEXT,                       -- preenchido no logout (AF-02) / reset (AF-03)
  CONSTRAINT sessions_token_hash_unique UNIQUE (token_hash)
);
CREATE INDEX sessions_user_id_idx ON sessions(user_id);
```

Decisões:
- O e-mail é gravado já normalizado (`trim().toLowerCase()`), e o `UNIQUE` incide sobre essa coluna. Assim a unicidade sem diferenciar maiúsculas (critério 5) fica garantida pelo banco (critério 6), de forma portável e sem depender de `COLLATE NOCASE` ou `citext`. Guardar a grafia original não traz valor para o produto e por isso foi descartado.
- O banco guarda apenas o hash SHA-256 do token de sessão. Quem tiver acesso de leitura ao banco não consegue sequestrar sessões.

## 5. Interfaces

### 5.1 API

**`POST /api/accounts`** (cadastro)

Request (`Content-Type: application/json`, corpo de até 16 KB):
```json
{ "name": "Ana Souza", "email": "Ana@Exemplo.com ", "password": "abcd1234" }
```

Respostas:

| Status | Quando | Corpo |
|---|---|---|
| 201 | conta criada | `{ "user": { "id", "name", "email", "createdAt" }, "redirectTo": "/onboarding" }` mais o header `Set-Cookie: af_session=...` |
| 400 | validação | `VALIDATION_ERROR` com `fields` para cada campo inválido (todos de uma vez) |
| 409 | e-mail já existe (inclusive em corrida) | `{ "error": { "code": "EMAIL_TAKEN", "message": "Este e-mail já está cadastrado.", "fields": { "email": "Este e-mail já está cadastrado." } } }` |
| 415 | content-type diferente de JSON | formato padrão |
| 429 | rate limit | `RATE_LIMITED` |

O corpo de resposta nunca contém `password` nem `passwordHash`. Isso é garantido pela função `toPublicUser(user)` do repositório, que é o único caminho para serializar um usuário.

Cookie: `af_session=<token base64url de 32 bytes>; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800`, mais `Secure` quando `cookieSecure` estiver ativo.

**`GET /api/me`** (sessão atual; usada para provar o critério 2 e pelo onboarding)

- 200 `{ "user": { "id", "name", "email", "createdAt" } }`
- 401 `UNAUTHENTICATED` sem cookie, com cookie desconhecido, expirado ou revogado.

**Páginas (estáticas)**: `GET /cadastro` serve `web/cadastro.html`, `GET /onboarding` serve `web/onboarding.html` e `GET /` redireciona (302) para `/cadastro` até existir a home. Os arquivos estáticos de `web/` são servidos em `/` e `src/shared/` em `/shared/`, para o browser importar `validation.js`.

### 5.2 Validação compartilhada (`src/shared/validation.js`)

Módulo puro, sem imports, usado pelo serviço e pelo browser:

```js
export const NAME_MAX = 100;
export const EMAIL_MAX = 254;
export const PASSWORD_MIN = 8;
export const PASSWORD_MAX_BYTES = 72;          // limite do bcrypt

export function normalizeEmail(raw)            // -> string (trim + lowercase); não-string -> ''
export function validateName(raw)              // -> string | null (mensagem de erro ou null)
export function validateEmail(raw)             // -> string | null
export function validatePassword(raw)          // -> string | null
export function validateSignup(input)          // -> { ok: true, value: { name, email, password } }
                                               //  | { ok: false, fields: { [campo]: mensagem } }
```

Regras e mensagens:
- **name**: obrigatório depois do `trim`, com 1 a 100 caracteres. São rejeitados caracteres de controle (`/[\u0000-\u001F\u007F]/`). Valor salvo: o nome com `trim`. Mensagens: "Informe seu nome." / "O nome deve ter no máximo 100 caracteres." / "O nome contém caracteres inválidos."
- **email**: obrigatório e normalizado, com até 254 caracteres. Regex pragmática `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`. Mensagens: "Informe seu e-mail." / "Informe um e-mail válido."
- **password**: precisa ser string. Não aplicamos `trim`, porque espaços fazem parte da senha. Regras: no mínimo 8 caracteres (`[...pw].length`), no máximo 72 bytes UTF-8 (`new TextEncoder().encode(pw).length`), ao menos uma letra (`/\p{L}/u`) e ao menos um dígito (`/\d/`). A mensagem descreve o requisito inteiro, para o usuário saber o que falta: "A senha deve ter no mínimo 8 caracteres, com pelo menos uma letra e um número." No caso do limite de bytes: "A senha deve ter no máximo 72 caracteres."
- Campos que não são string (número, objeto, null) são tratados como ausentes ou inválidos e nunca causam exceção.

### 5.3 Backend

```js
// src/modules/auth/password.js
export async function hashPassword(plain, cost)        // -> string bcrypt
export async function verifyPassword(plain, hash)      // -> boolean (usado no AF-02)

// src/modules/accounts/users.repository.js
export function createUsersRepository(db) -> {
  insert({ id, name, email, passwordHash, createdAt }),   // lança UniqueViolationError
  findById(id),                                           // -> User | undefined (inclui passwordHash)
  findByEmail(email),                                     // -> User | undefined (AF-02)
}
export function toPublicUser(user) // -> { id, name, email, createdAt }

// src/modules/auth/sessions.repository.js
export function createSessionsRepository(db) -> {
  insert({ id, userId, tokenHash, createdAt, lastSeenAt, expiresAt }),
  findActiveByTokenHash(tokenHash, nowIso),   // revoked_at IS NULL AND expires_at > now
}

// src/modules/auth/sessions.service.js
export function createSessionsService({ sessionsRepository, config, now = () => new Date() }) -> {
  createSession(userId),          // -> { token, expiresAt }  (token = randomBytes(32).toString('base64url'))
  resolveSession(token),          // -> { userId, sessionId } | null
}
// O refresh de last_seen_at/expires_at (inatividade) fica para o AF-02.

// src/modules/accounts/accounts.service.js
export function createAccountsService({ usersRepository, sessionsService, config, now }) -> {
  async signup(input) // -> { user: PublicUser, session: { token, expiresAt } }
                      // lança ValidationError(fields) | ConflictError('EMAIL_TAKEN', ...)
}

// src/modules/auth/auth.plugin.js  (fastify-plugin style, registrado em app.js)
// - decorateRequest('user', null)
// - onRequest: lê cookie af_session -> resolveSession -> request.user = PublicUser
// - exporta requireAuth(request, reply) para preHandler de rotas protegidas

// src/app.js
export async function buildApp(overrides = {}) // -> FastifyInstance (já com migrações aplicadas)
```

Fluxo do `signup`:
1. `validateSignup(input)`. Se falhar, lança `ValidationError(fields)`.
2. `passwordHash = await hashPassword(password, config.bcryptCost)`.
3. `usersRepository.insert(...)` com `id = randomUUID()`. Não fazemos `SELECT` prévio de unicidade: a constraint é a única fonte de verdade, o que elimina a corrida entre verificação e inserção. Um `UniqueViolationError` com constraint `users_email_unique` vira `ConflictError('EMAIL_TAKEN')`.
4. `sessionsService.createSession(user.id)`.
5. Retorna `toPublicUser(user)` e a sessão. A rota coloca o cookie e responde 201 com `redirectTo: '/onboarding'`.

Os passos 3 e 4 rodam na mesma `db.transaction`, para não sobrar um usuário sem sessão se a criação da sessão falhar.

### 5.4 Frontend

- `web/cadastro.html`: formulário com `name` (`autocomplete="name"`, `maxlength=100`), `email` (`type=email`, `autocomplete="email"`), `password` (`type=password`, `autocomplete="new-password"`, `minlength=8`), um texto de ajuda com o requisito da senha e um `<p class="field-error" aria-live="polite">` por campo, além de uma área de erro geral. Não há JS nem CSS inline, porque a CSP bloqueia.
- `web/js/signup-controller.js` (testável no Node, sem DOM):
  ```js
  export async function submitSignup(values, { fetchFn, navigate }) // -> { ok: true } | { ok: false, fields, message }
  ```
  Ele valida antes com `validateSignup`, vindo de `/shared/validation.js`. Faz `POST /api/accounts` com `credentials: 'same-origin'`. Com 201, chama `navigate(body.redirectTo)`. Com 400/409, devolve `fields` do servidor. Com erro de rede ou 5xx, devolve uma mensagem genérica.
- `web/js/signup-page.js`: liga o `submit` ao controller, desabilita o botão enquanto envia e escreve os erros **sempre com `textContent`**.
- `web/onboarding.html` + `onboarding-page.js`: chama `GET /api/me`. Com 401, redireciona para `/cadastro`. Com 200, mostra "Olá, {nome}" via `textContent` e um aviso de que o onboarding chega no AF-05.
- `web/css/app.css`: mobile-first, com largura útil a partir de 360 px, campos de 100% da largura, alvos de toque de pelo menos 44 px e `@media (min-width: 768px)` para centralizar o cartão.
- Proibido no frontend: `innerHTML`, `outerHTML`, `insertAdjacentHTML` e `document.write`. Um teste verifica isso (ver 6).

## 6. Plano de testes (critério para cobertura de critério)

`test/helpers/test-app.js` exporta `buildTestApp(overrides)`. Ele chama `buildApp({ databasePath: ':memory:', bcryptCost: 4, cookieSecure: false, rateLimit: { enabled: false }, logStream, ...overrides })` e devolve `{ app, logs }`, onde `logs()` retorna o texto capturado dos logs. Cada teste fecha o app no `after`.

| Arquivo | Casos | Critérios |
|---|---|---|
| `test/unit/validation.test.js` | `abcd1234` aceita; `abcdefgh`, `12345678` e `abc1234` rejeitadas com a mensagem do requisito; 73 bytes rejeitada; nome vazio, só espaços, com 101 caracteres ou com caracteres de controle; e-mail vazio ou inválido; `normalizeEmail(' Ana@X.com ') === 'ana@x.com'`; tipos não-string não lançam exceção | 7, 8, 9, 13, 5 |
| `test/unit/password.test.js` | hash diferente da senha, começa com `$2`, `verifyPassword` dá true para a senha certa e false para a errada | 11 |
| `test/integration/users.repository.test.js` | inserir o mesmo e-mail duas vezes direto no repositório lança `UniqueViolationError` (prova que a constraint está no banco, sem passar pelo serviço) | 6 |
| `test/integration/accounts.api.test.js` | 201 com corpo e `Set-Cookie` HttpOnly; `redirectTo === '/onboarding'`; `GET /api/me` com o cookie devolvido dá 200 e o mesmo usuário; sem cookie dá 401; e-mail duplicado dá 409 `EMAIL_TAKEN` e `COUNT(*)` continua 1; `Ana@x.com ` depois de `ana@x.com` dá 409; **duas requisições simultâneas** (`Promise.all` com dois `app.inject`) dão exatamente um 201 e um 409, nenhum 500, e uma linha no banco; 400 com `fields` para cada campo inválido; a senha nunca aparece nos corpos de 201/400/409 nem em `logs()`, e `passwordHash` também não; `password_hash` no banco é diferente da senha e passa no `verifyPassword`; nome `"Robert'); DROP TABLE users;--"` é salvo literalmente e a tabela continua existindo; nome `<script>alert(1)</script>` é salvo e devolvido literalmente em JSON; content-type `text/plain` dá 415; resposta com header CSP | 1, 2, 4, 5, 6, 10, 11, 12, 13, 14 |
| `test/integration/rate-limit.test.js` | com `rateLimit.enabled: true` e `signupMax: 2`, a 3ª requisição dá 429 | mitigação de enumeração |
| `test/web/signup-controller.test.js` | com `fetchFn` falso: 201 chama `navigate('/onboarding')`; 409 devolve `fields.email`; senha inválida não chama `fetchFn` | 3, 10 |
| `test/web/no-unsafe-dom.test.js` | lê `web/js/*.js` e falha se encontrar `innerHTML`, `outerHTML`, `insertAdjacentHTML` ou `document.write` | 14 |

Sobre o teste de concorrência: o `node:sqlite` é síncrono, mas o `hashPassword` é assíncrono. As duas requisições passam juntas pela validação e pelo hash e chegam ao `INSERT` intercaladas. Sem `SELECT` prévio, o segundo `INSERT` bate na constraint. É exatamente o cenário do critério 6.

Não há E2E com navegador real nesta fase, porque Playwright exige baixar browsers. O fluxo de tela é coberto pelo controller. E2E pode entrar junto com o AF-20.

## 7. Riscos

| # | Risco | Mitigação |
|---|---|---|
| R1 | `node:sqlite` ainda é experimental (warning, API pode mudar) | Ele fica isolado em `src/db/sqlite.js`. O plano B é trocar por `better-sqlite3`, que tem API quase idêntica, mudando só esse arquivo. Fixar `engines.node >=22.13`. |
| R2 | Mensagem de e-mail duplicado permite enumerar contas (decisão de produto do backlog) | Aceito conforme a história. Mitigação: rate limit de 10 cadastros por minuto por IP em `POST /api/accounts`. Registrar a ressalva para o time de segurança. |
| R3 | bcrypt trunca senhas acima de 72 bytes | Validação rejeita senhas com mais de 72 bytes UTF-8 (não 72 caracteres, porque acentos ocupam 2 bytes). |
| R4 | `bcryptjs` é mais lento que o bcrypt nativo e bloqueia o event loop por cerca de 100 a 250 ms com custo 12 | O volume de cadastro é baixo. Usamos a API assíncrona, que fatia o trabalho. Se login ou cadastro virarem gargalo, trocar por `argon2` ou `bcrypt` nativo só dentro de `password.js` (a interface não muda). |
| R5 | CSRF no cadastro/sessão via cookie | `SameSite=Lax`, POST só com `application/json` (o Fastify responde 415 para outros tipos, o que impede POST cross-site por formulário simples) e sem CORS habilitado. Proteção completa por token CSRF fica para avaliar no AF-02. |
| R6 | XSS pelo nome | O frontend usa só `textContent` (há teste para isso), a CSP é `default-src 'self'` sem inline e a API responde só JSON. O nome é gravado como veio, sem sanitização destrutiva, e escapado na saída. |
| R7 | SQL injection | Todo SQL é parametrizado com `?` através do adapter. É proibido concatenar valores em SQL, e o code review deve verificar isso. Há teste com payload de injeção. |
| R8 | Diferenças SQLite x PostgreSQL ao trocar o banco | SQL portável (3.3), erros neutros (`UniqueViolationError`), datas como ISO UTC e UUID gerado na aplicação. |
| R9 | Usuário criado sem sessão se a criação da sessão falhar | `insert` do usuário e da sessão na mesma transação. |

## 8. Decisões registradas (ADR curto)

1. **Monólito Node + Fastify servindo a API e o frontend estático.** Um processo e uma porta, sem CORS. Separar o front depois é possível, já que ele só conversa via `/api`.
2. **JavaScript ESM sem TypeScript.** Sem etapa de build. Os contratos são documentados em JSDoc. Pode ser revisto no AF-20 (`tsc --checkJs`).
3. **SQLite (`node:sqlite`) atrás de um adapter assíncrono com erros neutros.** Dá para trocar por PostgreSQL implementando `Database`.
4. **Unicidade de e-mail só pela constraint, sem pré-checagem.** Assim não há condição de corrida.
5. **E-mail persistido já normalizado** (trim + lowercase).
6. **Sessão opaca no servidor** (token em cookie HttpOnly, SHA-256 no banco) em vez de JWT, porque o AF-02 exige revogação no servidor.
7. **bcrypt via `bcryptjs`, custo 12** (configurável), com limite de 72 bytes na senha.
8. **Validação única compartilhada** (`src/shared/validation.js`). O backend é a autoridade e o frontend reusa o mesmo módulo.
9. **HTTP 400 para validação e 409 para e-mail existente**, com o formato de erro padrão da seção 3.1.
10. **Testes com `node:test`, banco `:memory:` por teste e `app.inject()`.** Um único comando: `npm test`.

## 9. Pontos em aberto respondidos

- Confirmação de e-mail: fora desta fase, conforme a história. O schema permite adicionar `email_verified_at` numa migração futura.
- Limites: nome até 100 caracteres; senha de 8 caracteres a 72 bytes.
- Enumeração no cadastro: aceita como decisão de produto, com rate limit (R2).
