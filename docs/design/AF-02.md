# Design AF-02 · Login e logout

História: docs/stories/AF-02.md · Status do design: proposto

Este design segue a stack, a estrutura de pastas e os padrões transversais definidos em docs/design/AF-01.md (seções 1 a 3). Aqui só aparece o que muda ou o que é novo. Nenhuma dependência nova de runtime ou de desenvolvimento.

---

## 1. Resumo da solução

- `POST /api/auth/login` valida as credenciais, aplica o bloqueio por tentativas, revoga a sessão anterior (se houver) e cria uma sessão nova com token novo.
- `POST /api/auth/logout` revoga só a sessão atual e limpa o cookie. É idempotente.
- A sessão passa a ter expiração deslizante (7 dias de inatividade) com teto absoluto (30 dias desde a criação).
- O bloqueio por tentativas fica numa tabela nova (`login_attempts`), com chave pela combinação e-mail + IP, contagem de falhas consecutivas e reserva atômica da tentativa antes do bcrypt.
- Um hook global de CSRF rejeita (403) requisições que alteram estado vindas de outra origem, checando `Sec-Fetch-Site` e `Origin`.
- `trustProxy` passa a ser configurável e `cookieSecure` passa a ser ligado por padrão.

Parse de `TRUST_PROXY` (função `parseTrustProxy(value)` em `config.js`):
- ausente, vazio, `false`, `0` → `false`
- `true` → `true` (confia em qualquer salto; só use se o proxy sobrescreve `X-Forwarded-For`)
- inteiro positivo → número de saltos confiáveis (recomendado: `1` atrás de um único proxy/load balancer)
- outro texto → lista de IPs/CIDRs separados por vírgula (ex.: `10.0.0.0/8,127.0.0.1`), repassada como array ao Fastify

`mergeConfig` passa a mesclar também `loginLock` (como já faz com `rateLimit`) e a remover `now` dos overrides, do mesmo jeito que já remove `logStream`.

`buildApp(overrides)` aceita `overrides.now` (função `() => Date`, padrão `() => new Date()`) e o repassa a todos os serviços. Isso dá o relógio controlável pedido no critério 10. `Fastify({ trustProxy: config.trustProxy, ... })` substitui o `trustProxy: false` fixo.

A configuração padrão e a recomendação de produção (`TRUST_PROXY=1` atrás de um proxy, `COOKIE_SECURE` não definido) ficam documentadas num `README.md` novo, seção "Configuração", e no JSDoc de `loadConfig` (critério 22).

Nota para dev local: Chrome e Firefox aceitam cookie `Secure` em `http://localhost`. Em outro navegador ou host, rode com `COOKIE_SECURE=false`.

## 3. Modelo de dados

`src/db/migrations/002_login_attempts.sql` (migração nova; a 001 não é editada):

```sql
CREATE TABLE login_attempts (
  key_hash      TEXT PRIMARY KEY,   -- SHA-256 hex de "<email normalizado>\n<ip normalizado>"
  failed_count  INTEGER NOT NULL,   -- falhas consecutivas (inclui tentativas em andamento, ver 5.3)
  locked_until  TEXT,               -- ISO-8601 UTC; NULL = sem bloqueio
  updated_at    TEXT NOT NULL
);
```

- A tabela `sessions` não muda: `last_seen_at`, `expires_at` e `revoked_at` já existem desde o AF-01.
- A chave é um hash, não o e-mail e o IP em claro. Isso evita guardar e-mails digitados por terceiros (inclusive de pessoas sem conta) e IPs, que são dados pessoais (minimização, LGPD). Para desbloquear manualmente, o operador calcula o mesmo hash.
- IP normalizado: o prefixo IPv4-mapeado `::ffff:` é removido (`::ffff:1.2.3.4` vira `1.2.3.4`). Agrupar IPv6 por /64 faz parte do item 3 da revisão de segurança e fica fora (ver R3).

## 4. Interfaces

### 4.1 API

**`POST /api/auth/login`**

Request (`application/json`, até 16 KB): `{ "email": "Ana@Exemplo.com ", "password": "abcd1234" }`

| Status | Quando | Corpo |
|---|---|---|
| 200 | credenciais corretas | `{ "user": { "id", "name", "email", "createdAt" }, "redirectTo": "/onboarding" }` mais `Set-Cookie: af_session=...` |
| 400 | e-mail ou senha ausentes, e-mail com formato inválido | `VALIDATION_ERROR` com `fields` (`email`, `password`) |
| 401 | e-mail inexistente **ou** senha incorreta | `{ "error": { "code": "INVALID_CREDENTIALS", "message": "E-mail ou senha inválidos." } }`, idêntico nos dois casos |
| 403 | origem diferente (CSRF) | `{ "error": { "code": "FORBIDDEN_ORIGIN", "message": "Requisição não permitida." } }` |
| 415 | content-type diferente de JSON | formato padrão |
| 429 | bloqueio por tentativas | `{ "error": { "code": "LOGIN_LOCKED", "message": "Muitas tentativas de login. Tente novamente em 15 minutos.", "retryAfterSeconds": 900 } }` mais header `Retry-After: 900` |
| 429 | rate limit por IP (20/min) | `RATE_LIMITED` (formato do AF-01) |

- `redirectTo` vem de `resolvePostLoginRedirect(user)` no serviço. Hoje sempre devolve `/onboarding`, porque ainda não existe negócio configurado. O AF-05 troca a regra só nessa função (critério 2).
- A mensagem de `LOGIN_LOCKED` usa os minutos restantes arredondados para cima (`Math.ceil(retryAfterSeconds / 60)`), com "1 minuto" no singular.

**`POST /api/auth/logout`**

Sem corpo e sem `Content-Type`. Sempre responde `204` (com ou sem sessão, com sessão expirada ou revogada) e envia `Set-Cookie: af_session=; Max-Age=0; Path=/; HttpOnly; SameSite=Lax` (mais `Secure` quando ativo). Só a sessão do cookie atual é revogada (critérios 17 a 19). Está sujeito ao CSRF (403).

**`POST /api/accounts`** (AF-01, alterado): passa a revogar a sessão anterior ativa (critério 20), a usar o helper de cookie comum (4.3) e a passar pelo hook de CSRF.

**`GET /api/me`** (AF-01): sem mudança de contrato. Passa a renovar a sessão (5.4).

**Páginas**: `GET /login` serve `web/login.html`. `GET /` passa a redirecionar para `/login` (antes `/cadastro`).

### 4.2 Extensão do formato de erro (3.1 do AF-01)

`src/http/errors.js` ganha:

```js
export class InvalidCredentialsError extends AppError   // 401 INVALID_CREDENTIALS, "E-mail ou senha inválidos."
export class ForbiddenOriginError extends AppError      // 403 FORBIDDEN_ORIGIN, "Requisição não permitida."
export class LoginLockedError extends AppError {        // 429 LOGIN_LOCKED
  constructor(retryAfterSeconds)                        // guarda this.retryAfterSeconds
}
```

`errorHandler`: quando `error.retryAfterSeconds` existir, envia o header `Retry-After` e inclui `retryAfterSeconds` em `error`. Essa é a única chave extra permitida além de `code`, `message` e `fields`; ela entra na tabela 3.1 como opcional. `UnauthorizedError` (401 `UNAUTHENTICATED`) continua sendo usado para sessão ausente ou inválida. `INVALID_CREDENTIALS` é usado só no login.

## 5. Fluxos

### 5.1 Login (`authService.login`)

1. `validateLogin(input)`. Se falhar, lança `ValidationError(fields)`. Nada é contado nem consultado (critério 8).
2. `key = attemptKey(email, ip)`. `reserve(key)`. Se `allowed` for false, lança `LoginLockedError(retryAfterSeconds)` **sem** verificar a senha, mesmo que ela esteja correta (critério 9).
3. `user = usersRepository.findByEmail(email)`.
4. `ok = await verifyPassword(password, user ? user.passwordHash : dummyHash)`, seguido de `ok = ok && Boolean(user) && byteLength(password) <= 72`. O bcrypt roda sempre, uma vez, com o mesmo custo, exista o e-mail ou não (critério 6). O limite de 72 bytes evita que o truncamento do bcrypt aceite uma senha mais longa que comece com a senha real.
5. Se `ok` for false, lança `InvalidCredentialsError()`. A falha já foi contada na reserva (5.3). O log registra só `{ event: 'login_failed' }` (sem e-mail, senha ou hash).
6. Se `ok` for true, abre uma `db.transaction` que executa `loginAttemptsService.clear(key)` (zera o contador, critério 11), depois `sessionsService.revokeSession(previousSessionId)` (critério 20) e por fim `sessionsService.createSession(user.id)`.
7. Retorna `toPublicUser(user)`, a sessão e `resolvePostLoginRedirect(user)`. A rota chama `setSessionCookie` e responde 200. O log registra `{ event: 'login_succeeded', userId }`.

`dummyHash`: gerado uma vez na criação do serviço com `hashPassword(<texto aleatório>, config.bcryptCost)` e guardado como Promise. Assim ele tem o mesmo custo dos hashes reais.

Fixação de sessão (critério 4): o token é sempre gerado pelo servidor (`randomBytes(32)`) na hora do login. Um cookie forjado antes do login não existe na tabela e nunca passa a valer. Um cookie válido anterior é revogado no passo 6.

A rota passa `ip: request.ip` (que respeita `trustProxy`) e `previousSessionId: request.sessionId` (preenchido pelo `authPlugin` só se o cookie apontar para uma sessão ativa).

### 5.2 Logout

`authService.logout(request.sessionId)` chama `revokeSession`, que não faz nada quando o id é `null`. A rota sempre chama `clearSessionCookie` e responde 204. As outras sessões do mesmo usuário não são tocadas, porque a revogação é por `id` da sessão (critério 19).

### 5.3 Bloqueio por tentativas (`loginAttemptsService.reserve`)

Tudo dentro de uma única `db.transaction` (no SQLite, `BEGIN IMMEDIATE` mais a fila do adapter: as reservas são serializadas):

```
touch(key, now)                       // primeira instrução: cria a linha se não existir e trava a linha
row = find(key)
if row.lockedUntil && row.lockedUntil > now:
    return { allowed: false, retryAfterSeconds: ceil((lockedUntil - now) / 1000) }   // não altera nada: não prorroga
count = (row.lockedUntil && row.lockedUntil <= now) ? 0 : row.failedCount            // bloqueio vencido: recomeça
count = count + 1
lockedUntil = count >= maxFailures ? now + lockMinutes : null
update(key, { failedCount: count, lockedUntil, updatedAt: now })
return { allowed: true }
```

- **A tentativa é contada como falha antes do bcrypt** e só é desfeita (`clear`) se o login der certo. Isso torna o contador correto sob concorrência (critério 14): de 10 tentativas simultâneas, as 5 primeiras reservas passam e as outras 5 encontram `locked_until` no futuro e recebem 429 sem chegar ao bcrypt. Se o processo cair durante a verificação, a tentativa fica contada como falha (o sistema falha fechado).
- Na 5ª reserva o bloqueio já é gravado. Se a 5ª tentativa estiver certa, o `clear` remove o bloqueio. Se estiver errada, a 6ª fica bloqueada por 15 minutos contados a partir da 5ª.
- A chave independe de a conta existir, então e-mails inexistentes são bloqueados com a mesma resposta (critério 12).
- O estado fica no banco, então sobrevive a reinício (critério 13). O expirar sozinho é só a comparação com `now()`, sem job (critério 10).
- Portabilidade: começar por um `INSERT ... ON CONFLICT DO UPDATE` (aceito por SQLite e PostgreSQL) trava a linha também no PostgreSQL, e o `SELECT` seguinte não corre risco de corrida. Assim não é preciso `SELECT ... FOR UPDATE`, que o SQLite não aceita.

### 5.4 Expiração da sessão (`sessionsService.resolveSession`)

1. `findActiveByTokenHash(hash, now)` (como no AF-01: `revoked_at IS NULL AND expires_at > now`).
2. Se `now - lastSeenAt >= sessionTouchIntervalSeconds`, chama `touch(id, { lastSeenAt: now, expiresAt: min(now + sessionTtlDays, createdAt + sessionAbsoluteTtlDays) })`.
3. Retorna `{ userId, sessionId }`.

- Cada requisição autenticada renova o prazo (critério 15). O intervalo de 60 s só evita uma escrita a cada CSS ou JS carregado. O erro máximo da janela de inatividade fica em 60 s.
- Um único `expires_at` concentra as duas regras, então a consulta de sessão ativa não muda.
- O `Max-Age` do cookie passa a ser o teto absoluto (30 dias). Antes era 7 dias. Sem essa mudança, o navegador descartaria o cookie 7 dias depois do login mesmo com uso contínuo. Quem decide a validade é o servidor.

### 5.5 CSRF (`isSameOriginRequest`)

Aplicado a todo método diferente de GET, HEAD e OPTIONS (hoje: `POST /api/accounts`, `/api/auth/login` e `/api/auth/logout`):

1. Se houver header `Sec-Fetch-Site`, aceita só `same-origin`. `same-site`, `cross-site` e `none` dão 403.
2. Senão, se houver header `Origin`, aceita só se for igual a `new URL(`${request.protocol}://${request.host}`).origin` ou a um item de `config.allowedOrigins`. `Origin: null` dá 403.
3. Sem nenhum dos dois headers, aceita. Navegadores atuais sempre enviam `Origin` em POST cross-origin e `Sec-Fetch-Site` em toda requisição, então a ausência indica um cliente que não é navegador (curl, testes com `app.inject`), que não carrega cookie da vítima. É o mesmo critério do `CrossOriginProtection` do Go e da recomendação de "Fetch Metadata" da OWASP.

As camadas do AF-01 (SameSite=Lax, só JSON, sem CORS) continuam ativas. A checagem roda em `onRequest`, antes do parse do corpo e de qualquer acesso ao banco.

## 7. Riscos

| # | Risco | Mitigação |
|---|---|---|
| R1 | Ataque distribuído contra uma conta: com bloqueio por e-mail + IP, um atacante com N IPs tem 5N tentativas a cada 15 minutos | bcrypt custo 12, política mínima de senha do AF-01 e rate limit por IP no login (20/min). Risco aceito nesta fase. Evolução sugerida: limite global por e-mail com limiar alto (ex.: 100/h) que exija CAPTCHA em vez de bloquear, para não reabrir a negação de serviço. Registrar para o time de segurança. |
| R2 | Negação de serviço residual: quem compartilha o IP da vítima (mesma rede ou NAT) ainda consegue travar a conta dela por 15 minutos | Aceito. O alcance cai de "qualquer lugar da internet" para "a mesma rede". O bloqueio expira sozinho e não prorroga. |
| R3 | Rotação de IPv6 dentro do mesmo /64 contorna o bloqueio e o rate limit | Fora do escopo (item 3 da revisão do AF-01). A normalização do IP fica isolada em `normalizeIp` dentro de `login-attempts.service.js`, e o agrupamento por /64 entra ali sem mudar a interface. |
| R4 | `TRUST_PROXY=true` sem proxy na frente deixa o cliente forjar `X-Forwarded-For` e escapar do bloqueio | Padrão `false`. O README recomenda o número de saltos (`1`) ou a lista de IPs do proxy, e não `true`. Há teste dos dois modos. |
| R5 | Crescimento da tabela `login_attempts` (tentativas com e-mails aleatórios) | Uma linha por par e-mail + IP, com o rate limit por IP limitando o ritmo de criação. Limpeza periódica (ex.: apagar linhas sem bloqueio e sem uso há 30 dias) fica para uma história de manutenção. A semântica de "consecutivas" não depende dela. |
| R6 | Enumeração de contas continua possível pelo 409 do cadastro (decisão de produto do AF-01) | O login não acrescenta nenhum canal novo: mesma resposta, mesmo custo de bcrypt e mesmo bloqueio. A ressalva continua registrada no AF-01 (R2). |
| R7 | Escrita no banco a cada requisição autenticada | O `touch` só acontece se a última atualização tiver mais de 60 s. |
| R8 | `COOKIE_SECURE` passa a ser `true` por padrão e pode quebrar o login em dev por HTTP fora de `localhost` | Documentado no README (`COOKIE_SECURE=false` em dev). Em produção o valor `false` é recusado na inicialização. |
| R9 | Cliente que não é navegador e não envia `Origin` passa pela checagem de CSRF | Esse cliente não tem o cookie da vítima, então não existe CSRF. Navegadores sempre enviam os headers checados. |
| R10 | O `Max-Age` do cookie passa de 7 para 30 dias | A validade real continua no servidor (7 dias de inatividade). O cookie mais longo só impede que o navegador o descarte antes da hora. |
| R11 | Reserva pessimista: uma tentativa correta concorrente com a 5ª errada pode receber 429 | Comportamento conservador e raro (exige 5 tentativas simultâneas no mesmo par e-mail + IP). |

## 8. Decisões registradas (ADR curto)

1. **Bloqueio pela combinação e-mail + IP** (sugestão do gerente, mantida). Evita que um terceiro trave a conta de outra pessoa de qualquer lugar (o problema de negação de serviço citado na história) e continua cobrindo o critério 9, cujos testes usam o mesmo IP. Isso é uma leitura mais estreita do texto "para o mesmo e-mail" e precisa do aceite do PO. O limite adicional por IP, proposto na história para ataques distribuídos, é o rate limit de 20 logins por minuto por IP (`@fastify/rate-limit`, já usado no cadastro).
2. **Falhas consecutivas, sem janela de tempo.** O contador só zera com login bem-sucedido ou com o fim de um bloqueio. É a regra mais simples de testar e de explicar, e corresponde ao texto do critério 9.
3. **Tentativa durante o bloqueio não prorroga o prazo.** Prorrogar daria a um atacante um jeito de manter o bloqueio para sempre.
4. **Tentativa contada antes do bcrypt (reserva atômica).** É o que garante o critério 14 sem lock em memória, e funciona com vários processos porque usa a transação do banco.
5. **Chave do bloqueio guardada como SHA-256**, sem e-mail nem IP em claro (minimização de dados).
6. **Expiração: 7 dias de inatividade mais teto absoluto de 30 dias.** O teto limita o tempo de vida de um token vazado mesmo que ele continue em uso. As duas regras convivem num único `expires_at`.
7. **Renovação da sessão com intervalo de 60 s**, para não gravar no banco a cada arquivo estático.
8. **Cookie com `Max-Age` igual ao teto absoluto** e validade decidida pelo servidor.
9. **CSRF por Fetch Metadata e `Origin`, sem token.** Não exige estado nem mudança no frontend, cobre todas as rotas que alteram estado com um único hook e se soma às camadas do AF-01. Token sincronizador foi descartado por complexidade sem ganho real neste cenário (mesma origem, sem CORS, navegadores atuais). `Referer` não é usado, porque pode ser suprimido e o `Origin` já cobre o caso.
10. **Revogação da sessão anterior só no login ou cadastro bem-sucedido**, na mesma transação que cria a sessão nova. Numa tentativa que falha, o cookie do navegador não muda, então a sessão antiga continua coerente com ele.
11. **`trustProxy` configurável, padrão `false`**, e **`cookieSecure` padrão `true`**, recusando `false` em produção.
12. **Rotas `/api/auth/login` e `/api/auth/logout`** no módulo `auth`, seguindo o padrão routes/service/repository. O logout é um POST, não um GET, para passar pelo CSRF e não ser disparado por um link.
13. **`validateLogin` sem regras de força de senha**, para que uma mudança futura na política não impeça quem já tem conta de entrar.
14. **Código `INVALID_CREDENTIALS` (401)** separado de `UNAUTHENTICATED`, para o front distinguir "credencial errada" de "sessão ausente", sem diferenciar e-mail inexistente de senha errada.
15. **`GET /` redireciona para `/login`**, porque o usuário recorrente é o caso comum. A página de cadastro ganha um link para entrar, e a de login um link para criar conta.

## 9. Pontos em aberto respondidos

- Bloqueio por e-mail, IP ou os dois: pela combinação e-mail + IP, mais rate limit por IP (decisão 1, riscos R1 e R2). Depende do aceite do PO.
- Falhas consecutivas ou em janela: consecutivas (decisão 2).
- Tentativa durante o bloqueio prorroga? Não (decisão 3).
- Limite absoluto da sessão: sim, 30 dias, configurável (decisão 6).
- Mecanismo de CSRF: Fetch Metadata e `Origin` (decisão 9).
- Itens 3 e 5 da revisão de segurança do AF-01 (custo do bcryptjs e IPv6 /64; caracteres invisíveis no nome): fora deste item. Sugestão: criar uma história técnica separada. O R3 registra o impacto do IPv6 sobre o bloqueio.
- Tela de login: formulário simples com e-mail e senha e link para o cadastro. O link "esqueci minha senha" entra com o AF-03.
