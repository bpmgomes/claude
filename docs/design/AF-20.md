# Design AF-20 · Pipeline de CI

História: docs/stories/AF-20.md · Status do design: proposto

Este design segue docs/design/AF-01.md (seções 1 a 3) e as decisões de teste de navegador de docs/design/AF-09.md (decisão 1 e R1: o Playwright fica fora do `package.json`). Aqui só aparece o que é novo. **Nenhum código de produto muda** em `src/modules/`, `src/app.js` ou `web/`. Exceção: as violações reais que o lint apontar, corrigidas sem mudar comportamento (4.3). **As dependências de runtime não mudam.** Entram três `devDependencies` (ESLint), um workflow, um script de smoke e documentação.

**Estimativa: 3 pontos** (decisão 10 do gerente). Se o primeiro pipeline exigir trabalho extra grande, o developer registra o achado na seção 11 e pede reestimativa (decisão 6).

---

## 1. Resumo da solução

- **Um workflow**, `.github/workflows/ci.yml`, com os jobs `lint`, `test` (matriz de `TZ`), `e2e` (matriz de `TZ`), `build-check`, `audit`, `perf` e o agregador `ci-ok`. Ele roda em `pull_request` (qualquer base), em `push` para `claude/project-thread-5e1ja7` e `main`, em `workflow_dispatch` e, só para o `audit`, toda semana (`schedule`).
- **Segurança do workflow**: `permissions: contents: read` no nível do workflow e nenhuma permissão a mais em job algum. Não usa `pull_request_target` nem segredo algum. O checkout é feito com `persist-credentials: false`. Só entram actions da organização `actions/` (mantidas pelo GitHub), fixadas por tag de versão maior (3.3). Não há action de terceiros.
- **Lint**: ESLint 9 com flat config (`eslint.config.js`), `@eslint/js` `recommended` e três regras a mais (`no-unused-vars` ajustada, `eqeqeq`, `no-var`). Não entra nenhuma regra de estilo. Script `npm run lint` = `eslint . --max-warnings 0`.
- **"Build" = `build-check`** (decisão 1): script versionado `scripts/smoke.js` (`npm run smoke`). Ele migra um banco temporário, sobe `node src/server.js` com configuração de produção e um `CONFLICTS_TOKEN_SECRET` gerado no próprio job, confere `GET /api/nao-existe` → 404 JSON e encerra o servidor.
- **E2E sem mudar a decisão do AF-09**: o Playwright é instalado só no job (`npm install --no-save playwright@$PLAYWRIGHT_VERSION`). O Chromium vem de `npx playwright install --with-deps chromium`, com cache de `~/.cache/ms-playwright`.
- **`ci-ok` é o único check a exigir na proteção**. Ele depende de `lint`, `test`, `e2e` e `build-check`. `audit` (decisão 3) e `perf` (decisão 4) são informativos.
- **Prova de que o pipeline detecta falhas** (critério 17, ajustado em 2.2): local, com falhas injetadas numa cópia fora do repositório, mais a primeira execução real verde no GitHub depois do push. Nenhum commit quebrado vai para a branch padrão.

## 2. Ajustes nos critérios da história

### 2.1 Gatilhos (critério 1, decisão 2)

O `push` filtra `branches: [claude/project-thread-5e1ja7, main]`. Se o dono criar `main` e torná-la padrão, o CI já roda nela sem editar o `ci.yml`. Se a branch padrão mudar para outro nome, a lista precisa de uma linha a mais, e o README avisa isso. Não se usa `github.event.repository.default_branch`, porque filtros de `on.push.branches` não aceitam expressões.

### 2.2 Critério 17 reescrito (decisão do gerente)

> 17. A capacidade de detectar falhas é provada em duas partes, sem empurrar commit quebrado para a branch padrão:
> (a) **Local**: numa cópia do repositório fora da árvore de trabalho, o developer roda os mesmos comandos de cada job com uma falha injetada por vez. São cinco falhas: (a1) variável não usada em `src/`, (a2) teste unitário quebrado, (a3) teste que só quebra com `TZ=Asia/Tokyo`, (a4) E2E quebrado, (a5) `CONFLICTS_TOKEN_SECRET` curto no smoke. Cada comando sai com código diferente de 0 e a mensagem esperada. Sem a falha, o mesmo comando sai com 0. A lógica do `ci-ok` também é testada com resultados simulados (6.2). Tudo vai para a seção 11.
> (b) **GitHub**: a primeira execução real de `ci.yml` depois do push na branch padrão termina verde, com todos os jobs de `ci-ok` em `success`. O gerente confere pela API (`GET /repos/{owner}/{repo}/actions/runs?branch=...&event=push`) e o link vai para a seção 11.
> A evidência no GitHub de um PR vermelho bloqueado fica com o dono, no critério 16.

### 2.3 Critérios que dependiam de "registrar no PR"

O time não abre PR (mesma prática do AF-22, decisão 7). O que a história manda registrar no PR vai para a seção 11 deste design e para o relatório do developer:
- **Critério 6** (violações corrigidas e regras desligadas): seção 11.
- **Critério 11** (resultado do `npm audit`): seção 11.
- **Critério 12** (tempo): a primeira execução de push é medida com cache frio. As 3 execuções com cache aquecido vêm das próximas execuções de push e do PR de teste do dono (critério 16). O gerente registra quando elas existirem. Uma estimativa local por job também vai para a seção 11.
- **Critério 13** (cache hit): a partir da segunda execução de push.
- **Critério 18**: a execução verde de push é a do 17 (b). A execução verde em PR fica com o dono (PR de teste do critério 16, depois de corrigido).

## 3. Workflow `.github/workflows/ci.yml`

### 3.1 Estrutura

O esqueleto abaixo é a referência da implementação. Ele é configuração e não código de produto. Nomes de jobs, gatilhos, permissões, timeouts e a lógica do `ci-ok` são obrigatórios. Os textos dos passos podem variar.

```yaml
# AF-20: CI. Único check a exigir na proteção de branch: ci-ok (README, seção CI).
name: CI

on:
  pull_request:            # qualquer base; nunca pull_request_target (sem segredos para forks)
  push:
    branches: [claude/project-thread-5e1ja7, main]   # branch padrão atual e main, se vier a existir
  schedule:
    - cron: '0 9 * * 1'    # segunda, 06:00 em São Paulo: só o job audit
  workflow_dispatch:

permissions:
  contents: read

# PR: um grupo por PR, e a execução nova cancela a antiga. Push, schedule e dispatch: grupo único
# por execução (run_id), então nada é cancelado nem enfileirado na branch padrão.
concurrency:
  group: ci-${{ github.event_name == 'pull_request' && github.ref || github.run_id }}
  cancel-in-progress: true

defaults:
  run:
    shell: bash            # explícito: bash -eo pipefail (o "tee" do e2e depende do pipefail)

env:
  PLAYWRIGHT_VERSION: 'X.Y.Z'   # a mesma do ambiente local (3.4); fixa, nunca "latest"

jobs:
  lint:            # timeout-minutes: 10; if: github.event_name != 'schedule'
  test:            # matriz tz; timeout-minutes: 15; if: != schedule
  e2e:             # matriz tz; timeout-minutes: 15; if: != schedule
  build-check:     # timeout-minutes: 10; if: != schedule
  audit:           # timeout-minutes: 10; todos os eventos
  perf:            # timeout-minutes: 15; if: github.event_name == 'push'; continue-on-error: true
  ci-ok:           # timeout-minutes: 5; if: always() && github.event_name != 'schedule'
```

### 3.2 Passos por job

Passos comuns, nesta ordem, em todos os jobs, com `runs-on: ubuntu-latest`:
1. `actions/checkout@v5` com `persist-credentials: false`.
2. `actions/setup-node@v5` com `node-version: '22'` e `cache: npm`. A chave do cache vem do `package-lock.json`.
3. `node --version && npm --version`, para registrar a versão efetiva (decisão 9).
4. `npm ci` (nunca `npm install` para o projeto, nunca `--omit=optional`). O `audit` não precisa deste passo (ver a tabela).

| Job | Passos próprios | Observações |
|---|---|---|
| `lint` | `npm run lint` | |
| `test` | `npm test` | `strategy.fail-fast: false`. Matriz `include: [{ tz: UTC, label: utc }, { tz: Asia/Tokyo, label: tokyo }]`. `env: TZ: ${{ matrix.tz }}` no job. `name: test (${{ matrix.tz }})` |
| `e2e` | 1. `npm install --no-save "playwright@$PLAYWRIGHT_VERSION"`. 2. `actions/cache@v4` (`id: pw`) com `path: ~/.cache/ms-playwright` e `key: playwright-${{ runner.os }}-${{ env.PLAYWRIGHT_VERSION }}`. 3. Se `steps.pw.outputs.cache-hit != 'true'`: `npx playwright install --with-deps chromium`. Senão: `npx playwright install-deps chromium`. 4. `npm run test:e2e 2>&1 \| tee "$RUNNER_TEMP/e2e-output.txt"`. 5. `if: failure()`: `actions/upload-artifact@v4` com `name: e2e-${{ matrix.label }}`, `path: $RUNNER_TEMP/e2e-output.txt` e `test-results/`, `if-no-files-found: ignore` e `retention-days: 7` | A mesma matriz e o mesmo `fail-fast: false` do `test` (decisão 8). O nome do artefato usa `label`, porque `/` (`Asia/Tokyo`) não é aceito em nome de artefato. Sem `retries` (decisão 7) |
| `build-check` | 1. `echo "::add-mask::$s"` e `echo "CONFLICTS_TOKEN_SECRET=$s" >> "$GITHUB_ENV"`, com `s=$(openssl rand -base64 32)` (44 caracteres). 2. `npm run smoke` | Segredo de uso único, gerado e mascarado no job. Não é segredo do repositório |
| `audit` | sem `npm ci`. 1. `npm audit` com `continue-on-error: true` (relatório completo no log, inclusive `devDependencies` e `moderate`/`low`). 2. `npm audit --omit=dev --audit-level=high`, que decide o resultado do job | Fora do `ci-ok` (decisão 3). O `npm audit` usa só o `package-lock.json`. Uma falha deixa a execução vermelha e visível, sem bloquear o merge |
| `perf` | os passos 1 a 3 do `e2e`. Depois, `PERF_REPORT="$RUNNER_TEMP/perf-report.json" npm run perf`. Por fim, `if: always()`: `upload-artifact@v4` de `$RUNNER_TEMP/perf-report.json*`, com `name: perf-report` e `retention-days: 30` | Só em `push` (decisão 4). `continue-on-error: true` no job, então uma oscilação não deixa a execução vermelha. Os relatórios de 30 dias alimentam a reavaliação de 2 semanas |
| `ci-ok` | sem checkout nem Node. `needs: [lint, test, e2e, build-check]`. Um passo com `env: NEEDS: ${{ toJSON(needs) }}` lista `job: result` e sai com 1 se algum resultado não for `success`: `jq -e 'all(.[]; .result == "success")' <<< "$NEEDS"` | `name: ci-ok`, que é o nome exigido na proteção. Com `if: always()`, ele também roda (e falha) quando um job necessário falha, é cancelado ou pulado |

Notas:
- **`TZ` vale para o processo inteiro do job**: o servidor Node e o Chromium iniciado pelo Playwright herdam o fuso. Isso reproduz o que o AF-11 fez localmente.
- **`npm install --no-save` depois do `npm ci`** coloca `playwright` em `node_modules` sem tocar no `package.json` nem no `package-lock.json`. O `createRequire` de `test/browser/playwright.js` o encontra pela resolução normal. A instalação não usa `--omit=optional`, então o binário do `sharp` fica intacto.
- **Sem cache de `node_modules`** (critério 13): só o cache do npm (`~/.npm`, via `setup-node`) e o de navegadores.
- **Os passos repetidos ficam duplicados no YAML** (setup em 7 jobs e Playwright em 2). Não há composite action local: o arquivo fica legível de cima a baixo e a revisão é mais simples. Se o AF-21 ou outro item acrescentar jobs, a extração vira item futuro.
- **Não há `paths-ignore`.** Uma mudança só em `docs/` também roda o pipeline. Se houvesse filtro, o `ci-ok` não rodaria, e um check exigido ausente trava o merge.

### 3.3 Versões das actions (critério 3)

| Action | Tag | Motivo |
|---|---|---|
| `actions/checkout` | `v5` | maior atual conhecida, roda em Node 24 |
| `actions/setup-node` | `v5` | maior atual conhecida. O cache automático por `packageManager` não se aplica (o `package.json` não tem esse campo), e `cache: npm` fica explícito |
| `actions/cache` | `v4` | maior conhecida com certeza |
| `actions/upload-artifact` | `v4` | maior conhecida com certeza |

Regra para o developer: antes de commitar, conferir a última versão maior de cada uma (`gh api repos/actions/<nome>/releases/latest --jq .tag_name`). Se houver uma maior estável (por exemplo, `cache@v5`), usar essa. A tag escolhida e a data da conferência ficam num comentário no topo do `ci.yml`. **Tag de versão maior, e não SHA**, porque todas são da organização `actions/`, mantida pelo GitHub. Fixar por SHA sem Dependabot (fora de escopo) deixaria as actions envelhecerem sem aviso. O comentário do `ci.yml` registra essa escolha (critério 3). Se um dia entrar uma action de terceiros, ela vai por SHA completo com a tag em comentário.

### 3.4 Versão do Playwright e do Node

- `PLAYWRIGHT_VERSION` é a mesma versão já usada no ambiente local, onde os E2E do AF-11 e do AF-22 passaram (`node -p "require('playwright/package.json').version"`, lido onde o pacote está instalado). Ela precisa ser 1.45 ou mais nova, para que `install-deps` suporte o Ubuntu 24.04 do `ubuntu-latest`. O valor e o motivo ficam em comentário ao lado da variável.
- **Node `'22'`, e não `node-version-file: package.json`** (decisão 9). O projeto só declara `engines.node: ">=22.13"` e não tem `.nvmrc`. Ler o `engines` resolveria para a versão mais nova que satisfaz `>=22.13`, ou seja, Node 24 ou superior, e não 22. Não se cria `.nvmrc` nesta história: a linha 22 é a que o projeto suporta, e a versão efetiva aparece no log de todos os jobs (passo 3).

## 4. Lint

### 4.1 Dependências e scripts (`package.json`)

- `devDependencies`, instaladas com `npm install -D`, o que atualiza o `package-lock.json` no mesmo commit:
  - `eslint`: `^9` (a última 9.x; **não** a 10, que a história não pede);
  - `@eslint/js`: `^9`, a mesma linha do `eslint`;
  - `globals`: a versão maior atual.
  As versões exatas resolvidas vão para a seção 11.
- `scripts`: `"lint": "eslint . --max-warnings 0"` e `"smoke": "node scripts/smoke.js"`.
- `dependencies` e `engines` não mudam.

### 4.2 `eslint.config.js` (novo, ESM, porque o `package.json` tem `"type": "module"`)

```js
// AF-20: lint mínimo, sem regras de estilo (critério 6). Ver README, seção CI.
import js from '@eslint/js';
import globals from 'globals';

export default [
  { ignores: ['data/', 'coverage/', 'test-results/', 'playwright-report/'] },
  js.configs.recommended,
  {
    languageOptions: { ecmaVersion: 'latest', sourceType: 'module' },
    linterOptions: { reportUnusedDisableDirectives: 'error' },
    rules: {
      'no-unused-vars': ['error', {
        argsIgnorePattern: '^_',
        varsIgnorePattern: '^_',
        caughtErrorsIgnorePattern: '^_',
        destructuredArrayIgnorePattern: '^_',
      }],
      eqeqeq: ['error', 'always'],
      'no-var': 'error',
    },
  },
  {
    files: ['src/**/*.js', 'test/**/*.js', 'scripts/**/*.js', 'eslint.config.js'],
    ignores: ['src/shared/**'],
    languageOptions: { globals: globals.node },
  },
  // Servido ao navegador em /shared/* e importado pelo servidor: só o que existe nos dois.
  { files: ['src/shared/**/*.js'], languageOptions: { globals: globals['shared-node-browser'] } },
  { files: ['web/**/*.js'], languageOptions: { globals: globals.browser } },
];
```

Notas:
- `node_modules/` e `.git/` já são ignorados pelo ESLint 9. `data/` vai explícito. Os relatórios do CI vão para `$RUNNER_TEMP`, fora da árvore, então nenhum artefato precisa entrar em `ignores` nem no `.gitignore`.
- **`reportUnusedDisableDirectives: 'error'`**: um `eslint-disable` que não suprime mais nada falha o lint. Assim não se acumulam diretivas mortas. O ESLint 9 já avisa por padrão, e isso falharia de qualquer forma com `--max-warnings 0`; deixar explícito evita a surpresa.
- `ignoreRestSiblings` fica no padrão (`false`). Os `eslint-disable-next-line no-unused-vars` existentes em `src/config.js:177` (desestruturação com `...rest`), `src/modules/auth/auth.service.js:30` (`now`) e `src/modules/businesses/businesses.service.js:49` (`config`) continuam necessários e válidos.
- `src/app.js:135`: com `varsIgnorePattern: '^_'`, o `_secret` da linha 136 não gera mais aviso. A diretiva da linha 135 fica sem uso e falha o lint. A correção é **remover essa linha de comentário**, sem outra mudança.
- `caughtErrors` fica no padrão do ESLint 9 (`'all'`, com exceção para `_`). Um `catch (err)` que não usa `err` vira `catch {` (optional catch binding, sem efeito no comportamento).

### 4.3 Como tratar as violações atuais (critério 6)

Levantamento prévio feito na leitura do código: nenhuma ocorrência de `==`/`!=` não estrito nem de `var` em `src/`, `web/` e `test/`. `eqeqeq` e `no-var` devem nascer limpos. O volume real só aparece ao rodar o lint, e o procedimento é este:

1. Rodar `npx eslint . --format json -o "$TMPDIR/lint.json"` e contar as violações por regra.
2. Para cada regra com **mais de 20** violações, desligar a regra (ou a opção dela, no caso de `caughtErrors`: `caughtErrors: 'none'`) com um comentário `// AF-20: desligada, N violações; ver BACKLOG <item>`. Depois, abrir o item de backlog técnico no BACKLOG.md, na seção "Técnico, bugs e spikes", com o título "Lint: religar <regra>".
3. Para as demais regras, corrigir uma a uma, **sem mudar comportamento**: remover import ou variável realmente não usada, `catch (err)` → `catch {`, prefixo `_` em argumento posicional exigido pela assinatura, ou remover a diretiva morta (4.2). Se uma correção exigir mudar lógica, ela não entra: o achado vira bug separado e é suprimido com `eslint-disable-next-line` mais um comentário com o id do bug.
4. `no-undef` (do `recommended`) em `test/web/` indica um teste que usa um global de navegador simulado. A correção é o comentário `/* global document */` no arquivo, e não trocar os `globals` do diretório inteiro.
5. Commits separados: (i) ESLint, configuração e script, (ii) correções das violações, uma regra por commit quando houver muitas, (iii) workflow, smoke e README. A lista "arquivo:linha, regra, correção" vai para a seção 11.

Depois da correção, `npm test` e `npm run test:e2e` precisam passar nos dois fusos, para mostrar que nada mudou.

## 5. Smoke `scripts/smoke.js` (critério 8)

Pasta nova `scripts/`, para ferramentas que não são da aplicação nem testes do `node:test`. O padrão de CLI é o mesmo de `src/db/migrate.js`: a função é exportada e o bloco de CLI fica protegido por `fileURLToPath(import.meta.url) === process.argv[1]`.

### 5.1 Interface

```js
/**
 * Sobe a aplicação como em produção e confere que ela responde (AF-20, critério 8).
 * @param {{ env?: NodeJS.ProcessEnv, bootTimeoutMs?: number, log?: (msg: string) => void }} [options]
 * @returns {Promise<void>} resolve se tudo passou; rejeita com Error cuja mensagem nunca contém segredos
 */
export async function runSmoke(options) {}
```

A CLI chama `runSmoke()`. Em erro, imprime `smoke: FALHOU: <motivo>` e sai com código 1. Em sucesso, imprime `smoke: ok (<ms> ms)` e sai com 0.

### 5.2 Fluxo

1. `mkdtemp(join(tmpdir(), 'agendafacil-smoke-'))`, com `DATABASE_PATH=<dir>/db.sqlite` e `UPLOADS_DIR=<dir>/uploads`.
2. Ambiente do filho: começa de `process.env`, força `NODE_ENV=production`, **remove `COOKIE_SECURE`**, define `PORT` (5.3), `PUBLIC_BASE_URL=https://smoke.invalid` (se não vier no ambiente) e os dois caminhos do passo 1. `CONFLICTS_TOKEN_SECRET`: se estiver **definido** no ambiente, é repassado como veio, mesmo curto ou vazio, o que permite injetar a falha (a5). Se estiver ausente, o script gera `randomBytes(32).toString('base64')` (44 caracteres), e o mesmo comando funciona localmente sem preparo.
3. `node src/db/migrate.js` (`spawn` com `process.execPath`, `stdio: 'inherit'`) e espera código 0, com teto de 30 s. Isso prova as migrações num banco vazio.
4. `node src/server.js` com o mesmo ambiente. O `buildApp` roda `runMigrations` de novo (nada pendente, o que prova a idempotência), carrega o `sharp` (import estático em `src/images/square-image.js`) e valida a configuração de produção (`resolveConflictsTokenSecret`, `COOKIE_SECURE`).
5. Até `bootTimeoutMs` (padrão 30 s), a cada 250 ms: se o filho saiu, falha com `servidor encerrou durante a subida (código N)`. Senão, tenta `fetch('http://127.0.0.1:<port>/api/nao-existe')` e ignora `ECONNREFUSED`.
6. Asserções: status 404; `content-type` começa com `application/json`; corpo `{ error: { code: 'NOT_FOUND' } }`; `cache-control: no-store`. Extra, de custo desprezível: `GET /login` responde 200 `text/html`, o que prova que `web/` é servido. Cada falha tem mensagem própria.
7. Espera 500 ms e confere que o filho continua vivo (`exitCode === null`).
8. `SIGTERM`. O `src/server.js` fecha o app e sai com 0. O script espera até 10 s; se o filho não sair, usa `SIGKILL` e falha. Se ele sair com código diferente de 0, também falha.
9. `finally`: mata o filho se ainda estiver vivo e remove o diretório temporário.

### 5.3 Porta

`net.createServer().listen(0, '127.0.0.1')` lê a porta livre, fecha o servidor e repassa a porta em `PORT`. A janela de corrida entre fechar e o filho ouvir é desprezível num runner dedicado. Se acontecer, o resultado é uma falha explícita de subida, e não um falso verde. Não se usa `PORT=0`, porque o script precisaria ler o log para descobrir a porta.

### 5.4 Por que não reaproveitar `test/browser/server.js`

Aquele helper chama o `buildApp` em processo, com `cookieSecure: false`, storage em memória e o segredo de teste. Ele não passa por `src/server.js`, por `loadConfig(process.env)` nem pela validação de produção, que são justamente o que o `build-check` precisa provar.

## 6. Plano de verificação local

Tudo roda no ambiente local do developer, com Node 22. Os scripts descartáveis ficam num diretório temporário fora do repositório e não são commitados.

### 6.1 Comandos dos jobs (árvore limpa)

```
npm ci
npm run lint
npm test
TZ=Asia/Tokyo npm test
npm run test:e2e
TZ=Asia/Tokyo npm run test:e2e
npm run smoke
CONFLICTS_TOKEN_SECRET="$(openssl rand -base64 32)" npm run smoke
npm audit --omit=dev --audit-level=high
npm run perf
```

Todos precisam sair com 0, exceto o `audit`, cujo resultado é registrado como veio (critério 11). Para cada comando, registrar o tempo, que serve de estimativa para o critério 12.

### 6.2 Falhas injetadas (critério 17 a)

Preparação: `cp -a` do repositório (com `node_modules`) para `$TMPDIR/af20-faults/`. Em cada caso, aplicar só a alteração indicada na cópia, rodar o comando e desfazer com `git checkout -- .` dentro da cópia, ou copiando de novo.

| # | Falha injetada na cópia | Comando | Esperado |
|---|---|---|---|
| a1 | `const unused = 1;` dentro de uma função de `src/modules/accounts/accounts.service.js` | `npm run lint` | código 1, `no-unused-vars` com arquivo e linha (critério 7) |
| a2 | `assert.equal(1, 2)` num teste de `test/unit/slug.test.js` | `npm test` | código 1, teste nomeado |

**Lógica do `ci-ok`**: extrair o comando `jq` do passo para um script descartável e rodá-lo com `NEEDS` simulado. Todos `success` → 0. Um `failure` → 1. Um `cancelled` → 1. Um `skipped` → 1. A saída lista `job: result`.

**Validação estática do YAML**: se o `actionlint` estiver disponível no ambiente, rodar `actionlint .github/workflows/ci.yml`. Em qualquer caso, um script descartável, com o pacote `yaml` instalado no diretório temporário (e não no projeto), confere que:
- não existe `pull_request_target`;
- `permissions` é exatamente `{ contents: 'read' }` e nenhum job declara `permissions`;
- todo job tem `runs-on: ubuntu-latest` e `timeout-minutes` com os valores de 3.1;
- todo `uses:` casa `^actions/[a-z-]+@v\d+$`;
- `ci-ok.needs` é `[lint, test, e2e, build-check]` e `ci-ok.if` contém `always()`;
- nenhum `run:` contém `--omit=optional`, `npm install` sem `--no-save` nem `|| true`.
