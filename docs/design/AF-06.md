# Design AF-06 · Cadastro de serviços

História: docs/stories/AF-06.md · Status do design: proposto

Este design segue a stack, a estrutura de pastas e os padrões transversais de docs/design/AF-01.md (seções 1 a 3) e as extensões de docs/design/AF-02.md e docs/design/AF-05.md. Aqui só aparece o que muda ou o que é novo. **Não há dependência nova.**

---

## 1. Resumo da solução

- Novo módulo `src/modules/services/` (routes/service/repository) com a entidade `services`, ligada ao negócio do dono (`business_id`). O negócio é sempre derivado da sessão (`businessesRepository.findByOwnerId`); nenhuma rota aceita `businessId` do cliente.
- API REST em `/api/services`: listar (com filtro de estado), ler, criar, editar, desativar e reativar. **Não há DELETE** (decisão 8 do gerente): a requisição cai no not-found handler e devolve 404 sem tocar no banco.
- Preço guardado em **centavos inteiros** (`price_cents INTEGER`), convertido de texto em pt-BR (`50`, `50,5`, `50.50`) por aritmética de string, sem `parseFloat`. "Sob consulta" é uma coluna booleana própria (`price_on_request`), com `CHECK` no banco impedindo os dois estados ao mesmo tempo.
- Nome único por negócio sem diferenciar maiúsculas nem acentos, garantido por `UNIQUE (business_id, name_key)`, em que `name_key` é a forma normalizada do nome calculada na aplicação (mesma técnica portável do e-mail no AF-01 e do slug no AF-05).
- Limite de 100 serviços por negócio (ativos e desativados), checado dentro da mesma transação do `INSERT`.
- Desativar com agendamentos futuros é permitido, sem cancelar nada. A resposta traz `futureAppointmentsCount`, hoje sempre 0, por meio de uma porta injetável (`appointments`) que o AF-11 vai implementar.
- Contrato de estado para AF-09, AF-10 e AF-11: coluna `active` e as funções `findActiveByBusinessId` e `findBookable` no repositório. A cópia (snapshot) de duração e preço no agendamento fica para o AF-11 (decisão 4), com o formato já definido em `toServiceSnapshot`.
- **Correção da pendência 1 de docs/security/AF-05.md**: `guardsFor()` sai de `businesses.routes.js` e vira `createRouteGuards()` em `src/http/route-guards.js`, que devolve array `onRequest`, limitador por usuário e objeto `config` **novos a cada chamada**. Cada rota chama uma vez. As rotas do negócio, do logo e dos serviços passam a usar o helper.
- A tela `/servicos` deixa de ser placeholder e passa a ser a tela de serviços (criar, editar, desativar, reativar, filtrar). O onboarding já leva a ela (`NEXT_STEP_PATH = '/servicos'`, AF-05).

## 2. Correção do rate limit por rota (pendência 1 do AF-05)

### 2.1 Causa

`guardsFor(config, bucket)` é chamado uma vez por bucket, e o mesmo objeto é passado para várias rotas (`write` em `POST`, `PATCH` e `GET slug-availability`; `logo` em `PUT` e `DELETE`). O Fastify copia as opções da rota de forma rasa, então o array `onRequest` é o mesmo em todas. No `onRoute`, o `@fastify/rate-limit` faz `routeOptions.onRequest.push(hookHandler)` (node_modules/@fastify/rate-limit/index.js, `addRouteRateHook`). Resultado: o array compartilhado fica com `[requireAuth, userLimit, ipPOST, ipPATCH, ipSLUG]`, e o handler do plugin marca a requisição com `rateLimitRan`, então só o primeiro (`ipPOST`) roda. As três rotas contam no mesmo balde de IP do `POST`.

O limitador por usuário (`createUserRateLimit`) também é uma instância só por bucket. No AF-05 isso era intencional (balde `businessWrite` compartilhado), mas tem o mesmo efeito prático: a checagem de slug com debounce enquanto o dono digita consome o limite de salvar.

### 2.2 Solução

```js
// src/http/route-guards.js (novo)
import { requireAuth } from '../modules/auth/auth.plugin.js';
import { createUserRateLimit } from './user-rate-limit.js';

/**
 * Hooks e config de UMA rota para um bucket de `config.rateLimit` (ex.: 'businessWrite').
 * Cada chamada devolve objetos novos: array `onRequest`, limitador por usuário e `config`.
 * Nunca reaproveite o retorno entre rotas: o @fastify/rate-limit faz push no array
 * `onRequest` e só executa o primeiro handler que encontrar.
 * Não congelar o retorno (Object.freeze quebraria o push do plugin).
 * @param {object} config app.config
 * @param {string} bucket chave em config.rateLimit com { perUser, perIp }
 * @returns {{ onRequest: Function[], config: { rateLimit?: { max: number, timeWindow: string|number } } }}
 */
export function createRouteGuards(config, bucket)
// rateLimit.enabled=false -> { onRequest: [requireAuth], config: {} }
// senão -> { onRequest: [requireAuth, createUserRateLimit({ max: perUser, timeWindow })],
//            config: { rateLimit: { max: perIp, timeWindow } } }

/** Só autenticação, sem limite (leituras). Array novo a cada chamada. */
export function authOnly() // -> { onRequest: [requireAuth] }
```

Uso nas rotas: `app.post('/api/business', createRouteGuards(config, 'businessWrite'), handler)`, uma chamada por rota. Na rota do logo, `{ bodyLimit, ...guards, config: { ...guards.config, payloadTooLarge } }`, com `guards` próprio do `PUT` e outro do `DELETE`.

Semântica nova (decisão 12): **cada rota tem seus próprios contadores**, por IP e por usuário, com os valores do bucket. O bucket passa a ser só a configuração. O teto efetivo de escritas por usuário passa a ser `perUser × número de rotas` do bucket, o que continua baixo (30/min por rota).

Rotas GET registradas com rate limit também geram a rota HEAD automática do Fastify com as mesmas opções; o HEAD divide o contador com o GET da mesma URL. Isso é aceitável (mesmo recurso) e fica registrado no JSDoc.

## 4. Modelo de dados

`src/db/migrations/004_services.sql` (nova; 001 a 003 não são editadas):

```sql
CREATE TABLE services (
  id                TEXT PRIMARY KEY,                    -- UUID v4
  business_id       TEXT NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  name              TEXT NOT NULL,                       -- trim + NFC, até 100 code points, como digitado
  name_key          TEXT NOT NULL,                       -- serviceNameKey(name): sem acentos, minúsculas, espaços colapsados
  duration_minutes  INTEGER NOT NULL,
  price_cents       INTEGER,                             -- NULL só quando price_on_request = 1
  price_on_request  INTEGER NOT NULL DEFAULT 0,          -- 0/1
  active            INTEGER NOT NULL DEFAULT 1,          -- 0/1; contrato para AF-09, AF-10, AF-11
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL,
  CONSTRAINT services_duration_check
    CHECK (duration_minutes BETWEEN 15 AND 480 AND duration_minutes % 15 = 0),
  CONSTRAINT services_price_range_check
    CHECK (price_cents IS NULL OR price_cents BETWEEN 0 AND 9999999),
  CONSTRAINT services_flags_check
    CHECK (price_on_request IN (0, 1) AND active IN (0, 1)),
  CONSTRAINT services_price_state_check
    CHECK ((price_on_request = 1 AND price_cents IS NULL) OR (price_on_request = 0 AND price_cents IS NOT NULL)),
  CONSTRAINT services_business_id_name_key_unique UNIQUE (business_id, name_key)
);
CREATE INDEX services_business_id_active_idx ON services(business_id, active, name_key);
```

- A constraint única segue a convenção `<tabela>_<colunas>_unique`. A mensagem do SQLite (`UNIQUE constraint failed: services.business_id, services.name_key`) é reconstruída pelo `translateError` como `services_business_id_name_key_unique`. Nenhuma mudança no adapter.
- A unicidade vale para serviços ativos e desativados. Assim, reativar nunca colide com outro serviço (o ponto em aberto sobre reativação some), e criar um serviço com o nome de um desativado dá 409 com a orientação de reativá-lo (decisão 3).
- Os `CHECK` são defesa em profundidade: o serviço valida antes, então uma violação de `CHECK` é bug e vira 500 pelo caminho normal (não há tradução para `CHECK` no adapter). Todos são SQL portável (PostgreSQL aceita `%`, `BETWEEN` e `CHECK` nomeado).
- Booleanos como `INTEGER 0/1`, convertidos no `fromRow`. Não usamos `STRICT` (exclusivo do SQLite). Com afinidade `INTEGER`, um número JS inteiro é gravado como inteiro; o teste de repositório confere `typeof(price_cents) = 'integer'`.
- `ON DELETE CASCADE` acompanha a cadeia já existente (usuário → negócio). Quando o AF-11 criar `appointments`, a FK para `services` deve ser `ON DELETE RESTRICT`, e a exclusão de conta precisará tratar agendamentos (registrado em R6).
- O índice cobre a listagem ordenada (`WHERE business_id = ? ORDER BY active DESC, name_key, id`) e as consultas do AF-09/AF-10 (`business_id = ? AND active = 1`).

## 5. Interfaces

### 5.1 API

Todas as rotas `/api/services*` exigem sessão (`requireAuth`); sem sessão, 401 `UNAUTHENTICATED` e nada é lido ou gravado. Mutações passam pelo hook de CSRF existente (403 `FORBIDDEN_ORIGIN`, critério 16). Dono sem negócio recebe **409 `BUSINESS_REQUIRED`** ("Cadastre seu negócio antes de criar serviços.") em todas as rotas, e o front redireciona para `/onboarding` (critério 2).

Representação (só via `toOwnerService`, o único caminho de serialização):

```json
{ "id": "…", "name": "Corte masculino", "durationMinutes": 30,
  "priceCents": 5050, "priceOnRequest": false, "active": true,
  "createdAt": "…", "updatedAt": "…" }
```

`businessId` e `nameKey` não são expostos. `priceCents` é `null` se e somente se `priceOnRequest` for `true`. O front formata preço e duração (5.3).

O `:id` precisa casar o regex de UUID v4 (o mesmo de `LOGO_FILE_RE`, sem a extensão); senão 404 `SERVICE_NOT_FOUND`. Serviço de outro negócio e serviço inexistente dão a mesma resposta: 404 `SERVICE_NOT_FOUND`, "Serviço não encontrado." (critério 15). Nenhuma mensagem de erro repete valores enviados (critério 7).

**`GET /api/services?status=all|active|inactive`** (sem limite próprio, só `requireAuth`)

| Status | Quando | Corpo |
|---|---|---|
| 200 | sempre que houver negócio | `{ "services": [ … ] }`, ordenado por `active DESC, name_key ASC, id ASC` (estável) |
| 400 | `status` fora da lista | `VALIDATION_ERROR` com `fields.status` = "Filtro inválido." |

`status` ausente equivale a `all`.

**`GET /api/services/:id`**: 200 `{ "service": {…} }` ou 404.

**`POST /api/services`** (guards próprios, bucket `serviceWrite`)

Request (`application/json`, até 16 KB): `{ "name": "Corte masculino", "durationMinutes": 30, "price": "50,50" }` ou `{ "name": "Coloração", "durationMinutes": 120, "priceOnRequest": true }`. Qualquer outro campo (`businessId`, `active`, `id`, `priceCents`...) é ignorado.

- `durationMinutes`: número JSON inteiro. Texto (inclusive `"30"`), `30.5`, vazio, ausente e fora de 15..480 ou não múltiplo de 15 dão erro em `fields.durationMinutes`.
- `price`: texto ou número JSON (5.2). Ausente ou `null` = não informado.
- `priceOnRequest`: booleano JSON, padrão `false`. Outro tipo dá erro em `fields.priceOnRequest`.
- `priceOnRequest: true` com `price` informado → 400 em `fields.price` (critério 6). `priceOnRequest` falso sem `price` → 400 em `fields.price`.

| Status | Quando | Corpo |
|---|---|---|
| 201 | criado | `{ "service": {…} }` |
| 400 | validação (todos os campos de uma vez) | `VALIDATION_ERROR` com `fields` (`name`, `durationMinutes`, `price`, `priceOnRequest`) |
| 409 | nome já usado por serviço ativo | `{ "error": { "code": "SERVICE_NAME_TAKEN", "message": "Já existe um serviço com este nome.", "fields": { "name": "…" } } }` |
| 409 | nome já usado por serviço desativado | mesmo código, mensagem "Já existe um serviço desativado com este nome. Reative-o ou escolha outro nome." |
| 409 | negócio já tem 100 serviços | `SERVICE_LIMIT_REACHED`, "Você atingiu o limite de 100 serviços. Edite um serviço existente." |
| 409 | sem negócio | `BUSINESS_REQUIRED` |
| 429 | rate limit (usuário ou IP) | `RATE_LIMITED` |

**`PATCH /api/services/:id`** (guards próprios, bucket `serviceWrite`)

Request: subconjunto de `{ name, durationMinutes, price, priceOnRequest }`. Só os campos presentes (chave existe) são validados e gravados. Corpo sem nenhum deles → 400 "Nada para atualizar.". Regras do par preço/sob consulta, sempre autocontidas no próprio PATCH (sem depender do estado atual, para não haver corrida entre ler e gravar):

| Corpo | Resultado gravado |
|---|---|
| `price` válido, sem `priceOnRequest` | `price_cents = x`, `price_on_request = 0` |
| `price` válido e `priceOnRequest: false` | idem |
| `priceOnRequest: true`, sem `price` (ou `price: null`) | `price_cents = NULL`, `price_on_request = 1` |
| `priceOnRequest: true` e `price` informado | 400 `fields.price` |
| `priceOnRequest: false` sem `price` | 400 `fields.price` ("Informe o preço ou marque Sob consulta.") |
| `price: null` sem `priceOnRequest: true` | 400 `fields.price` |

Respostas: 200 `{ "service": {…} }`; 400; 404; 409 `SERVICE_NAME_TAKEN` (enviar o próprio nome atual, mesmo com outra caixa ou acento, não é conflito, porque a linha é a mesma); 429. Editar serviço desativado é permitido.

**`POST /api/services/:id/deactivate`** e **`POST /api/services/:id/reactivate`** (guards próprios cada uma, bucket `serviceWrite`; sem corpo)

- 200 `{ "service": {…}, "futureAppointmentsCount": 0 }` no deactivate; 200 `{ "service": {…} }` no reactivate.
- Idempotentes: desativar um desativado ou reativar um ativo responde 200 com o estado atual.
- 404 para inexistente ou de outro negócio; 429.
- Nada é cancelado ao desativar (decisão 1). `futureAppointmentsCount` vem da porta `appointments` (5.4) e hoje é sempre 0.

**`DELETE /api/services/:id`**: não registrada. Cai no not-found handler do app: 404 `NOT_FOUND`, a linha continua no banco (critério 13, decisão 8). O CSRF roda antes (`onRequest` global): com `Origin` de outro site, 403.

**Página**: `GET /servicos` continua servindo `web/servicos.html` (já está em `PAGES` e em `RESERVED_SLUGS`).

### 5.2 Validação, preço e formatação compartilhados (`src/shared/services.js`, novo, puro)

Usado pelo backend e pelo browser (`/shared/services.js`). Importa só `./validation.js` (`normalizeText`, `hasForbiddenChars`, `MESSAGES.nothingToUpdate`).

```js
export const SERVICE_NAME_MAX = 100;
export const DURATION_MIN = 15;
export const DURATION_MAX = 480;
export const DURATION_STEP = 15;
export const DURATION_OPTIONS;            // Object.freeze([15, 30, ..., 480]) -> 32 opções (select da tela)

export const SERVICE_STATUSES;            // Object.freeze(['all', 'active', 'inactive'])
export const SERVICE_MESSAGES;            // Object.freeze({...}) mensagens fixas (abaixo)

// Em partial=false, value sempre traz priceCents (number|null) e priceOnRequest (boolean).

```

`parsePriceToCents(raw)`, sem ponto flutuante em nenhum passo:
1. Número JSON: precisa ser finito; vira `String(raw)` (`50.5` → `"50.5"`; `1e21` → `"1e+21"`, rejeitado no passo 3). Outro tipo que não string → `priceInvalid`.
2. `trim`; vazio → `priceRequired`; mais de 20 caracteres → `priceInvalid` (corta antes do regex e de qualquer conversão).
3. Começa com `-` → `priceNegative`. Senão precisa casar `/^(\d+)(?:[.,](\d+))?$/`; senão `priceInvalid` (inclui `R$ 50`, `1.000,00`, `abc`, `50,`).
4. Parte decimal com mais de 2 dígitos → `priceDecimals` (`50,555`).
5. `cents = Number(inteiro) * 100 + Number(decimal.padEnd(2, '0'))`, com `inteiro` de até 7 dígitos após remover zeros à esquerda (mais que isso → `priceTooHigh` direto, sem converter). Todos os valores são inteiros seguros.
6. `cents > PRICE_MAX_CENTS` → `priceTooHigh`. `0` é aceito (gratuito, decisão 3).

Exemplos: `50` → 5000; `50,5` → 5050; `50.50` → 5050; `0,10` → 10; `0` → 0; `99999,99` → 9999999; `100000` → `priceTooHigh`; `50,555`, `-1`, `abc`, `""` → erro.

`formatPriceCents` usa só inteiros (`Math.trunc(cents / 100)`, `cents % 100`, `padStart`) e insere o separador de milhar à mão. Não usa `Intl.NumberFormat`, que põe U+00A0 entre `R$` e o número e varia entre versões de ICU.

Mensagens (`SERVICE_MESSAGES`, todas fixas, sem interpolar entrada):

| Chave | Texto |
|---|---|
| `nameRequired` | Informe o nome do serviço. |
| `nameTooLong` | O nome deve ter no máximo 100 caracteres. |
| `nameInvalid` | O nome contém caracteres inválidos. |
| `nameTaken` | Já existe um serviço com este nome. |
| `nameTakenInactive` | Já existe um serviço desativado com este nome. Reative-o ou escolha outro nome. |
| `durationRequired` | Informe a duração. |
| `durationInvalid` | A duração deve ser de 15 min a 8 h, em intervalos de 15 min. |
| `priceRequired` | Informe o preço ou marque "Sob consulta". |

O texto do nome é gravado como veio (após `trim` e NFC) e escapado na saída (`textContent`), como no AF-05. Injeção SQL coberta pelos placeholders.

## 6. Fluxos

### 6.1 Criação (`servicesService.create`)

1. `business = businessesRepository.findByOwnerId(ownerId)`; ausente → `ConflictError('BUSINESS_REQUIRED')`.
2. `validateServiceInput(input)`; erros → `ValidationError(fields)`.
3. `db.transaction(async (tx) => { if (await countByBusinessId(business.id, tx) >= 100) throw ConflictError('SERVICE_LIMIT_REACHED'); await insert({...}, tx); })`. A transação (`BEGIN IMMEDIATE` + fila do adapter) serializa contagem e `INSERT`: duas criações simultâneas com 99 serviços geram exatamente uma linha e um 409.
4. `UniqueViolationError` com `services_business_id_name_key_unique` → `findByNameKey` para escolher `nameTaken` ou `nameTakenInactive` → `ConflictError('SERVICE_NAME_TAKEN', msg, { name: msg })`. Sem `SELECT` prévio de nome: a constraint é a fonte de verdade (mesma decisão do AF-01 e AF-05).
5. A rota responde 201 com `toOwnerService`.

### 6.2 Edição (`update`)

1. Negócio (409 se não houver); `SERVICE_ID_RE` no id (404).
2. `hasServiceFields` (400 "Nada para atualizar."); `validateServiceInput(input, { partial: true })`.
3. `update(id, business.id, { ...value, updatedAt })` num único `UPDATE ... WHERE id = ? AND business_id = ?`. `changes = 0` → 404. Conflito de nome → 409 como em 6.1.
4. `findById` e 200.

Concorrência (critério 19, decisão 9): cada `UPDATE` é atômico e a fila do adapter serializa as escritas; a última vence. Não há leitura entre validar e gravar, então dois PATCH simultâneos nunca produzem estado misto (por exemplo, preço de um com "sob consulta" do outro): o par preço/sob consulta sempre vai inteiro no mesmo `UPDATE`, e o `CHECK` do banco garante. Sem controle de versão.

### 6.3 Desativar e reativar

1. Negócio e id como em 6.2.
2. `setActive(id, business.id, false|true, nowIso)`; `changes = 0` → 404. Repetir a operação atualiza só `updated_at` (idempotente para o cliente).
3. Deactivate: `futureAppointmentsCount = await appointments.countFutureByService(business.id, id, nowIso)`; nada é cancelado. Falha da porta não desfaz a desativação: é registrada no log (`service_future_count_failed`) e a resposta sai com `futureAppointmentsCount: null`, que o front trata como "não foi possível verificar". Hoje a porta nunca falha.
4. Reactivate não tem conflito de nome possível (unicidade cobre desativados).

### 6.4 Ordem dos hooks nas mutações

`onRequest` global: CSRF (403) e `authPlugin` → `onRequest` da rota: `requireAuth` (401) e limite por usuário da própria rota → limite por IP da própria rota (`@fastify/rate-limit`) → parser JSON (16 KB) → handler. Requisições sem sessão não consomem limite (já coberto no AF-05 e repetido para `POST /api/services`).

## 9. Decisões registradas (ADR curto)

1. **Desativar com agendamentos futuros é permitido, com aviso, sem cancelar** (decisão 1 do gerente). Porta `AppointmentsPort` com implementação nula até o AF-11; a resposta já traz `futureAppointmentsCount`.
2. **Nome único por negócio, sem maiúsculas e sem acentos** (decisão 2), por `UNIQUE (business_id, name_key)` com `name_key` calculado na aplicação. Portável, sem `COLLATE` nem extensão.
3. **A unicidade inclui desativados.** Reativar nunca conflita; criar com nome de desativado dá 409 orientando a reativar.
4. **R$ 0,00 aceito como gratuito** (decisão 3), distinto de "sob consulta".
5. **Preço em centavos inteiros**, convertido de texto por aritmética de string. Aceita vírgula ou ponto decimal, sem separador de milhar. Formatação também só com inteiros, sem `Intl`.
6. **"Sob consulta" é coluna própria**, com `CHECK` de exclusividade com o preço; enviar os dois é 400.
7. **Duração só como número JSON inteiro**, múltiplo de 15, de 15 a 480. Sem buffer e sem serviço acima de 8 h (decisão 7). A tela usa `<select>` com as 32 opções.
8. **Teto de R$ 99.999,99 e limite de 100 serviços por negócio** (decisão 6), o limite contando desativados e checado na mesma transação do `INSERT`.
9. **Sem DELETE** (decisão 8): rota não registrada, 404 do not-found handler. Desativar e reativar são ações próprias (`POST /:id/deactivate|reactivate`), idempotentes, em vez de `PATCH { active }`, para separar o aviso e os limites.
10. **Snapshot no agendamento fica para o AF-11** (decisão 4), com o formato definido aqui (`toServiceSnapshot`).
11. **Sob consulta pode ser agendado online** (decisão 5): `findBookable` não filtra por preço.
12. **Guards de rate limit próprios por rota**, com contadores próprios por IP e por usuário (fecha AF-05 item 1). O bucket de configuração é só o conjunto de valores.
13. **Última escrita vence** (decisão 9), sem versão; o par preço/sob consulta é sempre gravado junto para não haver estado misto.
14. **Dono sem negócio recebe 409 `BUSINESS_REQUIRED`** em todas as rotas de serviços; o front leva ao onboarding.
15. **Serviço de outro negócio e inexistente dão o mesmo 404**, e todo acesso no repositório filtra por `business_id`.
16. **Mensagens de erro fixas**, sem interpolar entrada (critério 7, e mesma linha do AF-05 item 6).
17. **Sem campo de descrição nesta história.** Os critérios pedem nome, duração e preço; descrição longa está fora de escopo. Se o AF-09 pedir descrição curta, entra em migração nova com a mesma regra de texto.
